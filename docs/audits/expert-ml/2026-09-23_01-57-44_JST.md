## 2. F1【新发现 · P1】单实例锁没有跨 scheduler 与直接研究入口共享

ID：`EML-P1-H504-SINGLE-INSTANCE-LOCK-NOT-SHARED-WITH-DIRECT-RUNNER`

### 2.1 源码事实

`scripts/run_fixup.py`：

- 定义 `local_lock(path)`；
- 正式启动时使用 `with local_lock(LOG_DIR/'agent.lock')`；
- 锁覆盖 sync、agent 启动和整个子进程等待期；
- 已启动 agent 的硬兜底是 13200 秒。

但 `src/ml/research_h504/run.py`：

- 没有 import `local_lock` 或任何跨进程锁；
- `--stage all` 会直接创建／写入 `experiment_registry.jsonl`、H504 模型／预测、AUX checkpoint、run summary、start/execution receipt；
- `h504-hgb` 和 `aux-tcn` 也都是可直接调用的训练入口。

`scripts/run_fixup.task.xml` 的 `MultipleInstancesPolicy=IgnoreNew` 只保护 Windows 计划任务自己的第二次触发；它不会拦住用户或本地 agent 另开一个命令行进程执行 `python -m src.ml.research_h504.run ...`。

### 2.2 为什么这是 P1，不只是“多跑一点”

v5 明确要求“单实例锁跨 runner/手动启动生效”。当前实现只完成了一半。

并发有两个失败面：

1. **相同 `--out`**：两个进程可同时操作同一个 `experiment_registry.jsonl`、`h504_T0/`、AUX `best.pt/last.pt`、receipt 与 summary。即使单次 `registry.append()` 通常是一行写入，也没有事务把“查 previous → fit → 写 artifact → append COMPLETE”绑定成原子过程；两边可以同时看到 `previous is None` 后重复训练，随后互相覆盖 artifact 或留下与 registry 不对应的最后文件。
2. **不同 `--out`**：文件不会直接覆盖，但仍能同时占 CPU/GPU/内存，并且当前全局48-fit门本来就尚未代码强制；两个 session 可分别认为自己还有预算，形成双重消耗。

因此这不是 scheduler 重复触发才会发生的问题；手工补跑、调试 CLI、本地 agent 内部再直接启动研究 runner 都能绕过 outer `agent.lock`。

### 2.3 最小修复

不要再新增第二套互不相干的锁。把非阻塞锁实现抽到一个共享模块，并令所有“会产生 fit/registry/checkpoint”的入口使用**同一个 repo-scoped lock path**，例如 `logs/fixup/research_session.lock`：

- `scripts/run_fixup.py` 在启动本地研究 agent 前拿锁；
- `src/ml/research_h504/run.py` 对 `all / h504-hgb / aux-tcn` 在任何训练或 registry 写入前拿同一把锁；
- `contract / inspect` 等真正只读阶段可不占锁；
- 锁冲突必须立即 `ALREADY_RUNNING` fail closed，不 sleep，不等待凑 active time；
- 退出／异常必须释放；仅清理本次持有的进程树。

### 2.4 验收

必须覆盖：

- outer launcher 已持锁时，direct runner 被拒绝；
- direct runner A 已持锁时，direct runner B 被拒绝；
- owner 正常退出后下一实例可以拿锁；
- Windows 与 POSIX 分支都有测试；
- 不改变任何 trigger、StartAt、task name、account。

本轮隔离候选用两个独立进程实测：持锁进程存在时第二进程抛 `ResearchAlreadyRunning`，释放后重新获取成功。

## 3. F2【新审计结论 · P1认证阻塞】`same_basis_required` 只是声明，REAL_MARKET 没有 basis 门禁

ID：`EML-P1-H504-PRICE-BASIS-CONTRACT-ADVISORY-ONLY`

### 3.1 代码写了“必须同基准”，但没有任何可验证输入

`src/ml/research_h504/task_spec.py` 的 `H504TaskSpec` 明确有：

```text
price_basis = 'same_basis_required'
```

但 `label_h504_candidates()` 只要求：

```text
code, date, open, close, low
```

随后直接计算：

```text
E = t+1 open
target = 4 * E
floor = 0.8 * E
goal = close > target
risk = low < floor
```

它没有接收／比较 `open_basis / low_basis / close_basis`，也没有读取任何 basis manifest。

`src/ml/research_h504/data_io.py::prepare_panel()` 也只要求裸 `code,date,open,high,low,close,volume`；CSV/Parquet reader 都没有 basis schema。

仓库自己的 `src/data_pipeline.py` 输出 panel manifest 时记录 rows/codes/date/source path 等，但没有 machine-verifiable `raw/qfq/hfq/total_return` 字段。

### 3.2 文档其实承认了限制，但 CLI 没把它变成门禁

`RESEARCH_QUICKSTART.md` 已写：

- “OHLC必须同一价格基准”；
- “读文件不自动认证 PIT、复权或成交可执行性”；
- “若真实日历或价格口径不明，先修数据合同”。

所以“价格基准需要核验”不是本轮第一次提出。**本轮新增的审计结论是：这个要求目前只停留在文档层；`--evidence-type REAL_MARKET` 不会因为 basis 缺失而 fail closed。**

这与 calendar guard 不一样：真实运行缺 `--calendar` 会直接 `BLOCKED_CALENDAR`；价格 basis 缺失却没有对应 `BLOCKED_PRICE_BASIS`。

### 3.3 风险机制

H504 的 4E 与 0.8E 都是**跨时点价格比例**。如果 E、Low、Close 来自不同复权／财富基准，比例本身失去合同含义，可以制造假的 success/risk/timeout。即使当前 Tencent 数据实际上是统一原始口径，只要 manifest 和 receipt 没有证明它，后续外部 `--panel` 仍可以无声换成另一种口径。

因此本项不是说“当前 tracked panel 已经混基准”；本轮没有真实 panel 字节和来源合同证明这一点。正确口径是：**REAL_MARKET 认证目前 fail-open，无法机器证明同基准；这是首个真实 fit 前必须补齐的 G1 门禁。**

### 3.4 最小修复

建议引入 basis contract，至少：

- REAL_MARKET 必须有显式 bundle basis：`raw | qfq | hfq | total_return`（名称可调整，但语义必须固定）；
- 若数据源提供逐列 provenance，则 `open/high/low/close` 必须都等于 bundle basis；任何混合立即 `BLOCKED_PRICE_BASIS_MIXED`；
- basis 绑定 panel fingerprint，写入 `data_inventory.json`、task/label manifest、experiment signature、start/execution receipt、模型/prediction manifest；
- 不允许从价格走势“猜”复权类型；
- raw / qfq / hfq / wealth 的实验与结果分开，不能共用 signature／registry COMPLETE。

### 3.5 验收

- REAL_MARKET 无 basis → fail closed；
- raw bundle + open/high/low/close 全 raw → pass；
- qfq bundle全 qfq → pass；
- raw open + qfq low/close → 在 label 前 fail；
- 同一 panel 字节但 basis 元数据改变 → experiment signature 改变，不复用旧 COMPLETE；
- SYNTHETIC 可以允许显式测试豁免，但 receipt 必须保持 `SYNTHETIC`。

本轮候选 contract tests 覆盖其中无 basis、同基准、混基准、synthetic 四个场景。
