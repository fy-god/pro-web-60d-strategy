## 1. 【已确认错误 · P0】`low504` 标签在真实停牌面板上**窗口错位**

### 1.1 事实（真实函数 + 真实 A 股面板）

`src/labels.py` 的入场与视界**都在「行空间」，而任务定义在「市场 session 空间」**：

```python
# src/labels.py
L124-128  entry = np.full(n, np.nan, dtype="float64")
          entry[:-1] = opens[1:]                       # <-- 下一【行】
          same_next = np.zeros(n, dtype=bool)
          same_next[:-1] = codes[1:] == codes[:-1]     # 只判「同股票」
          entry[~same_next] = np.nan
L161      for d in range(1, horizon + 1):              # <-- 扫【行】
L165      same[: n - d] = codes[d:] == codes[: n - d]  # 只判「同股票」
L176      future_bars[valid] += 1.0                    # <-- 数【行】
L196      resolved = (future_bars >= horizon) & np.isfinite(entry)
```

**只有「同股票」守卫，没有「相邻交易日」守卫。** 停牌股的缺失 session 在面板里**根本不存在**，
于是「下一行」= 复牌那一行，「H 行」= H 个**被观测到的** bar。

**真实复牌反例**（我本人用真实函数跑出）：

```text
code 002656（真实停牌股，面板内 799 行 / 886 sessions）
  停牌前一行  2023-04-28 (session 77)  open=1.99
  复牌那一行  2023-06-30 (session 117) open=2.16   gap = 40 sessions
  真实 labels.forward_outcomes(horizon=504, target_return=1.0)
    信号行 2023-04-28 的 entry_open = 2.16
    == 复牌日 2023-06-30 的 open ?  True
    该行 future_bars = 330.0  （以【行】计）
  该股另有 2024-11-08 (s=446) -> 2025-01-14 (s=492)，gap = 46 sessions
```

**`entry_open` 取的是 40 个 session 之后的复牌开盘价，不是任务定义的 next market session open。**

### 1.2 影响面（真实数据计量）

```text
面板 = mainboard_tencent_daily_2023_2024.csv + mainboard_tencent_daily_2025_20260828.csv
  2,677,525 行 / 3,193 codes / 886 sessions / 2023-01-03..2026-08-28

同股票相邻行对 2,674,332：
  gap > 1 session  =    941  (0.0352%)
  gap > 5          =    313
  gap > 20         =     15
  gap 最大值        =     46 sessions
  受影响股票        =    586 / 3,193 (18.35%)

视界错位（H 行实际覆盖的 session 跨度）：
  H=60   可成熟行 2,486,061     span>60 = 51,289 (2.0631%)   span>65 = 10,891   最大 108
  H=504  可成熟行 1,105,291     span>504 = 135,108 (12.2237%) span>509 = 45,694  最大 590
```

即：**已提交制度 `REGIMES["low504"]`（`labels.py:62`，H=504）的 12.2237% 成熟行，
实际覆盖了超过 504 个 session（最长 590）**；`low60` 有 2.0631%（最长 108）。
这不是理论风险，是当前代码在真实数据上的偏差。

### 1.3 机制 / 影响 / 修法 / 验收

- **机制**：面板按「有报价的行」存储，停牌直接缺行；标签代码以行序代替 session 序。
- **影响**：`low504` 的 12.22%、`low60` 的 2.06% 成熟行，其实际前视窗口**长于**声明值，
  使这两个 regime 的基准率与精确率**不可比**；入场价在 941 个位置上是复牌价（最远相隔数周），
  使 `forward_max_return` 的分母被替换成一个陈旧价格。
- **修法**：以 `REGIMES` 的 session 数为准，用独立交易日历把面板 reindex 到 session 网格
  （缺行保留 NaN），入场取 `session t+1`、视界数 session；或在计算前加**相邻 session 守卫**，
  对跨缺口的行显式标 `unknown` 而非静默沿用行序。
- **验收**：`H=60`/`H=504` 的成熟行 session 跨度满足 `max(span - H) == 0`；
  停牌构造（面板挖洞）下 `entry_open` 必须为 NaN 或显式 `no_entry`，不得取复牌价。
- **状态：已确认错误（P0）。**

## 2. 【已确认错误 · P0】`dedupe_signals` 的冷却时钟不是交易日历，**过度抑制**

### 2.1 事实

```python
# src/labels.py
L233  session_index = {d: i for i, d in enumerate(sorted(out["date"].unique()))}
L234  positions = out["date"].map(session_index).to_numpy()
L242  if last is None or (positions[j] - last) >= cooldown:
```

`session_index` 由**传入信号帧自身的 date 唯一值**构造（`out = signals.sort_values(...)`，L230），
**不是**交易所日历。我上一轮把这条记为 `EML-P0-COOLDOWN-INDEPENDENT-CLOCK`，本轮给出**准确量级与方向**。

### 2.2 决定性反例（真实函数）

```text
两个同股票信号 2023-01-03 与 2023-06-02（真实间隔 108 个交易日，> cooldown=60）
dedupe_signals(..., cooldown=60) -> 保留 1 行（应为 2 行）
```

**方向与量级**（稀疏信号帧，3 只股票 × 8 个信号 = 24 行，真实日历 886 session）：

```text
按【真实 session 距离】(设计语义) 应保留 = 15
按【帧内秩差】(labels.py:233 实际) 保留 =  3
dedupe_signals() 实测                 =  3      <-- 与帧内秩差口径精确一致
```

**缺陷方向是【过度抑制】over-suppression：24 个信号被压成 3 个，少保留 12 个。**
（机制：帧内秩差 ≤ 真实 session 距离，故 cooldown 比设计更早触发。）

### 2.3 影响

- `src/backtest_lowzone.py:206` 是真实调用点（`cooldown=horizon`）。传入的是**被选中的稀疏信号**，
  故该路径**恰好落在缺陷区**：冷却按「被选中日期的秩」而非「交易日」触发，**系统性吃掉信号**，
  使 `n = len(deduped)`（`:207`）偏小，进而 `_wilson(hits, n)`（`:211`）与所有以 n 为分母的
  精确率**小样本化**（置信区间变宽、点估计噪声放大）。
- **我未能量化生产影响**：`outputs/` 下**没有任何 `*signal*.csv`**（实测 0 个），
  故无法用真实信号文件统计。**此项记为未量化，不夸大。**

### 2.4 仓库自己知道

`tests/test_engine.py:228-232` 的 docstring **明文承认**该行为：

> Note the distance is measured over the dates OBSERVED in the signal frame
> (`session_index` is built from `sorted(out["date"].unique())`), not over
> the exchange calendar. … which is exactly why this fixture **plants a filler
> stock on every intervening session to make the grid dense**.

即：测试**必须**在每个中间 session 插入一只填充股票，断言才能通过（`:243-248`）。
**测试为适配缺陷而构造稠密网格** —— 这是「测试掩盖缺陷」的直接证据，
也是该缺陷至今未在生产上暴露的原因。

### 2.5 修法 / 验收

- **修法**：`session_index` 改为基于独立交易日历（或由调用方传入 `calendar`）；
  缺日历时**显式报错**，不得静默退化为帧内秩。
- **验收**：§2.2 反例（相距 108 session 的两个信号）必须保留 2 行；
  且**移除** `test_engine.py:243-248` 的填充股票后，该测试仍须通过。
- **状态：已确认错误（P0）。**

## 4. 【本轮主结论 · 否决性】`02-07-54` §2.3 的「887→0 折」算术正确，但**「数据不足」的解释不成立**

### 4.1 该模块**不在产品树里**（先确认前提）

**即：该模块是**未合入**的候选，任何「产品已因此阻塞」的说法都不成立。**

### 4.2 **算术是对的**（我独立闭式推导 + 暴力枚举）

```text
条件：train 需 i + H < D 且 i >= 0  ->  D >= H + 1
      dev   需 D + H <= N - 1      ->  D <= N - 1 - H
      存在解  <=>  H + 1 <= N - 1 - H  <=>  N >= 2H + 2
最小 N = 2H + 2 = 1010（H=504）     合法折数 = N - 2H - 1

N=880 ->0   N=887 ->0   N=1010 ->1   N=1091 ->82   N=1092 ->83   N=1200 ->191   N=1500 ->491
```

**887 < 1010 故 0 折；1200 > 1010 故 191 折。peer 的数字精确复现，最小 N=1010 由本轮补出。**
该条件等价于教科书式 purge：「训练行的**整个 504-session 计划视界**必须严格在 dev 开始前闭合」，
严格 `<` 相对 `<=` 多一个 session 的 embargo。

### 4.3 **但它的解释不成立 —— 我差一点又把兄弟仓库的修法错误平移**

## 7. 未修项回归

### 7.1 `EML-P0-AUDIT-FETCH-FAIL-PASS` —— **仍 OPEN**（本轮给出精确语义）

前几轮我把它记作「`:108` 忽略 `note`」。本轮逐行读完 `write_status` 后**更正为更精确的表述**：

```python
L108   ok = code == 0 and not unstable          # <-- note 不参与
L109   verdict = "PASS" if ok else "ATTENTION"
L141   f"| Remote drift | {note} |"              # <-- note 只被【显示】
L159   if changed: lines += ["## Remote drift", f"{note}:", ""]
L344   needs_attention = code != 0 or bool(changed) or bool(unstable)
```

**`note` 确实被读取并写进 `AUDIT_STATUS.md`，但它不参与 `verdict`，也不参与 `needs_attention`。**
而 `changed_reports()` 在 fetch 失败时返回 `([], "git fetch failed (exit N): …")`（`:85-86`）。

我用真实判定式复刻验证：

```text
fetch 失败           verdict=PASS  needs_attention=False   Remote drift 行="git fetch failed (exit 128): schannel ..."
fetch 成功+有drift    verdict=PASS  needs_attention=True    Remote drift 行="1 path(s) differ from origin/main"
fetch 成功+无drift    verdict=PASS  needs_attention=False   Remote drift 行="0 path(s) differ from origin/main"
一致性检查失败         verdict=ATTENTION needs_attention=True
```

**即：`git fetch` 失败时，`changed` 为空 → `verdict` 仍为 `PASS`，`needs_attention` 为 False，
不写入 `FINDINGS`、不触发 attention 路径，只有表格里一行文字在说明失败。**
这正是「fetch 失败被判为 PASS」的确切机制，也是我上轮抱怨的 `git fetch` schannel 抖动
**为什么从未在 CI 里变成红灯**。

**当前证据**：`reports/AUDIT_STATUS.md` 本轮仍报
`Verdict **PASS**` / `Consistency check exit code 0` / `629 checks run, 0 problem(s)` /
`Remote drift 0 path(s) differ from origin/main`，而该文件在这批提交里**只被改了 4 行时间戳**。
即：**drift 检查在说谎时与说真话时，产出的判词完全相同。**

- **修法**：把 fetch 失败作为**独立失败信号**（例如让 `changed_reports` 返回三态，
  或让 `ok` 包含 `note` 的可信性），使 `verdict` 在 fetch 失败时为 `ATTENTION`/`UNKNOWN`。
- **验收**：模拟 fetch 失败（无网络 / 坏 remote）时 `AUDIT_STATUS.md` 的 `Verdict`
  **不得**为 `PASS`。
- **状态：仍 OPEN（P0）。**
