## 1. 新增 P1：`EML-P1-H504-REAL-CALENDAR-GUARD-SELF-REPORT-FAILOPEN`

### 位置

`src/ml/research_h504/run.py`：

- CLI `--evidence-type` 默认值为 `UNSPECIFIED`；可选值才包括 `REAL_MARKET / AUX_REAL_HISTORY / SYNTHETIC`。
- 只有当 `args.evidence_type in {'REAL_MARKET','AUX_REAL_HISTORY'}` 时，缺少 `--calendar` 才会 `BLOCKED_CALENDAR`。
- 默认 `UNSPECIFIED` 不触发该守卫，随后 `independent_cal=None`，`prepare_panel(..., None)` 直接从 panel 日期并集推导日历。
- 同一 `UNSPECIFIED` 还进入 `ResearchSessionReceipt`，因此真实训练即使发生，`receipts.py` 也不会把训练秒数计入 `real_train_seconds`。

`src/ml/research_h504/data_io.py` 又明确把 `calendar=None` 的分支实现成 `normalize_calendar(p.date)`；而 `task_spec.market_calendar()` 的 docstring 明确说 observed-union fallback 是 synthetic tests 用途，真实 CLI 应要求独立日历。也就是说，源码“意图”与入口“强制条件”不一致。

### 可执行反例已经存在于仓库测试

`tests/research_h504/test_candidate.py` 中：

1. `test_all_stage_runs_diagnostics_and_blocks_h504_without_candidate_manifest` 调用 `--stage all --panel ... --out ... --skip-neural`，**既不传 `--calendar`，也不传 `--evidence-type`**，当前断言 exit 0。
2. `test_cli_inspect_and_label_sample` 同样在无独立 calendar 下成功执行。
3. `test_all_stage_can_build_candidate_manifest_and_complete_h504_dev_fit` 使用 `--evidence-type SYNTHETIC` 且无 `--calendar`，证明 observed-union 路径不仅能做 inspect，也能走到 `COMPLETE_H504_DEV` 的完整训练路径。

因此，只要本地执行者把真实 A 股 panel 交给同一默认 CLI，却漏写 `--evidence-type REAL_MARKET`，程序没有任何自动机制区分“真实数据”与“synthetic”，会沿 synthetic fallback 使用 panel 日期并集。这个反例不需要猜测未来行为：入口的默认值与守卫条件已经形成确定的 fail-open 控制流。

### 影响

这是 H504 的时间协议问题，不是普通日志字段问题：

- 若授权行情缺某些全市场交易日、只含子宇宙或发生全局缺档，panel union 会把真实交易日从 market-session clock 中压缩掉，`t+1`、`t+504`、deadline、fold maturity 都可能按错误 session 序号计算。
- 同一误配置下 receipt 会写 `evidence_type=UNSPECIFIED`，真实训练秒数不进入 `real_train_seconds`，导致三小时执行证据账本与真实工作不一致。
- registry 仍可得到 `COMPLETE_*` 行；“不是 REAL_MARKET evidence”虽然限制了认证含义，但并不能阻止错误日历下的模型结果占用研究队列与拟合预算。

严重度定为 **P1**：它可以改变标签时间轴与 fold 支持，且由默认参数触发，不依赖数据泄漏或异常输入。

### 最小修复

建议把“真实/合成”从可选注释升级为入口类型系统：

1. 对 `all / h504-hgb / aux-tcn / label-sample` 等会产生研究证据的阶段，`UNSPECIFIED` 一律 fail-closed；要求显式选择 `REAL_MARKET / AUX_REAL_HISTORY / SYNTHETIC`。
2. `REAL_MARKET` 与 `AUX_REAL_HISTORY` 必须提供独立 `--calendar`，保持现有守卫。
3. `SYNTHETIC` 若允许 panel-union fallback，应明确记录 `calendar_source='panel_union_synthetic_only'`；最好再增加显式 `--allow-inferred-calendar`，避免单一 evidence 字段承担两种职责。
4. `data_inventory.json` 与 receipt 写入 `calendar_source / calendar_path / calendar_sha256`，不能只有 `calendar_hash`。

### 验收测试

- `--stage all` + panel + 无 evidence type → 必须失败 `BLOCKED_EVIDENCE_TYPE_UNSPECIFIED`。
- `--evidence-type REAL_MARKET` + 无 calendar → 继续失败 `BLOCKED_CALENDAR`。
- `--evidence-type REAL_MARKET` + 独立 calendar → 才允许进入候选/label/fold。
- `--evidence-type SYNTHETIC` + 显式允许 inferred calendar → synthetic smoke 继续可跑。
- receipt 对真实模式必须 `real_train_seconds == training_h504 + training_aux + ...`，不能因漏参数降成 0。

## 2. 新增 P1：`EML-P1-H504-AUX-FALLBACK-RUNS-WHEN-PRIMARY-READY`

### 位置与确定控制流

`src/ml/research_h504/run.py` 的 `--stage all`：

1. 有 candidate manifest 时先执行/复用 `h504_T0`。
2. 紧接着只判断 `if not args.skip_neural:`，随后无条件进入 `reps=[('base',...),('plus_research',...)]` 与 seed 循环。
3. 该分支**不检查** H504 结果是 `COMPLETE_H504_DEV`、`BLOCKED_PROTOCOL_H504`、`BLOCKED_CLASS_SUPPORT` 还是其他状态。
4. 默认 seeds=`17,29,43`、两个 representation、`--max-aux-fits=6`，因此一个首次运行、H504 T0 已合法完成的 session，默认仍可继续启动 **6 个 AUX-TCN fit**；连同 T0 即 7 个拟合调用。

### 为什么这是合同级缺陷

当前 v5 人工合同把 AUX 明确定义为：**H504 没有合法 full-followup fold 时的 fallback**。合法 H504 主任务存在时，优先队列应继续 WP4 的 T1–T5、WP5 的 H504 MLP/TCN、消融与误差驱动配对，而不是先把 6 个槽位给一步收益/5日波动的辅助目标。

目前产品只实现 T0 + AUX，尚未实现 T1–T5/H504 MLP/TCN；这并不意味着可以把“未实现的主任务”静默替换成 AUX。当前控制流会让 AUX 在两种完全不同的情形下都运行：

- H504 被协议阻塞：AUX 作为 fallback，**符合**合同。
- H504 已可运行甚至已 `COMPLETE_H504_DEV`：AUX 仍默认运行，**不符合**合同中的主任务优先级。

结合上一轮已确认的“48-fit 全局预算尚未代码强制”，这一行为会进一步放大预算漂移：辅助目标可能在主任务 READY 时先消耗 6 次拟合与大量 wall time。

### 影响边界

这条缺陷**不会直接伪造 H504 命中率**，因为 registry 已有 `task_scope=H504_JOINT/AUX_HISTORY`；因此不是标签泄漏类 P0。但它会改变三小时 session 的真实工作分配、fit 预算和“为什么主任务没有继续推进”的解释，故作为 **P1 execution-contract mismatch** 记录。

### 最小修复

- 先把 H504 主任务状态归一化为 `PRIMARY_READY / PRIMARY_BLOCKED / PRIMARY_COMPLETE_BUT_MORE_PREREGISTERED_WORK`。
- 默认仅在 `PRIMARY_BLOCKED` 时进入 AUX fallback。
- 若研究者确实希望在主任务 READY 时并行比较 AUX，必须显式预登记 `--run-aux-alongside-primary`，并计入 48-fit 台账；不能作为默认行为。
- 在 T1–T5/H504 MLP/TCN 尚未实现前，应返回 `NEEDS_IMPLEMENTATION` 队列状态，而不是用 AUX 自动填满剩余 session。

### 验收测试

用 monkeypatch 计数即可，无需真实训练：

1. `run_h504_hgb -> COMPLETE_H504_DEV`，默认 `--stage all`：`run_aux_tcn` 调用次数必须为 **0**。
2. `run_h504_hgb -> BLOCKED_PROTOCOL_H504`：AUX 按预登记 base/plus seeds 运行。
3. 显式 `--run-aux-alongside-primary`：主任务 COMPLETE 时 AUX 才允许启动，并且每次调用进入全局 fit 台账。
4. `run_summary.json` 写出 `queue_reason`，区分 `AUX_FALLBACK_PROTOCOL_BLOCK` 与 `AUX_PREREGISTERED_ALONGSIDE_PRIMARY`。
