## 0. 本轮结论先行

本轮没有新的 H504 实股拟合结果，`real_market_fit_count = 0`。但不是再次只写计划：在当前隔离沙箱中，已把上一候选实现继续推进成 **session-clock v2**，完成 24 项候选单测，并增加一个可在用户本机真实面板上直接运行的迁移影响探针。

本轮新实现解决四个具体问题：

1. **早成功／早风险与训练资格分离**：早终止事件可以在 `label_known_at` 提前知道，但保守完整随访 BCE 仍等到预登记 H504 deadline 才 `training_eligible`，不把近期早成功样本提前吸入训练。
2. **冷却严格使用独立市场 session 日历**：不再由稀疏信号帧自己的日期秩构造时钟；信号日期不在日历时 fail closed。
3. **FeatureSpec 补齐新 H504 oracle 的未来／结果元数据**：`target_price`、`risk_floor`、`training_eligible(_at)`、`candidate_id`、`signal_date` 等都禁止成为模型输入。
4. **fold-support 结论收窄**：H=504 的 dense full-follow-up BCE 最小会话数 `2H+2=1010` 只回答“当前提供的 calendar 能否形成完整随访 train→dev 折”，明确**不再外推成“用户本机没有更长历史”或“仓库其他 H10 任务也数据不足”**。

此外，新增 CLI 可对真实本地 panel 生成 `data_inventory.json`、`task_spec.json`、`fold_support.json`，并可跑小规模 session-label 迁移样本；新增 `compare_product_vs_session_oracle.py`，会优先抽取停牌/缺 session 股票与稠密对照股票，直接比较当前产品 row-clock 标签与 session oracle。

## 2. 本轮实际实施：H504 session-clock candidate v2

候选仍只存在当前隔离沙箱／本对话附件，不冒充产品已修。

### 2.1 `task_spec.py`：早终止知识与完整随访 BCE 资格分离

上一候选有一个我本轮主动发现的实现缺口：当 `t+504` deadline 超出当前观察 calendar 时，它会在扫描未来路径**之前**直接返回 `pending_maturity`。这虽然阻止了早成功样本提前进 BCE，但也把“已经发生的 success/risk”从 outcome ledger 里抹掉了。

v2 改为两条时钟：

```text
label_known_at        = 事件真正变成已知的时间；早 risk/success 可以提前
training_eligible_at  = 预登记完整随访 deadline；保守 BCE 只能到这里才入训
```

结果语义：

| 状态 | `label_joint` | `label_resolved` | `training_eligible` |
|---|---:|---|---|
| `success` 提前发生 | 1 | True | 只有 full deadline 已落入观察 calendar 才 True |
| `risk` 提前发生 | 0 | True | 同上，不提前入 BCE |
| 完整 504 日无终止 | 0 | True | True，known_at=deadline |
| horizon 未走完且无终止 | NaN | False | False |
| next market session 无有效 Open | NaN | False | False；不得顺延复牌 |
| 中途未知缺 bar/价格 | NaN | False | False |

这直接落实“结果知识”和“训练资格”分开：早 success/risk 可用于 outcome/accounting 诊断，但不会因为它们早知道，就相对 timeout 过度进入近期训练样本。

H504 primary spec 固定：

```text
entry = next market session valid Open E
success = first Close > 4E
risk = Low < 0.8E
same session: risk first
horizon = t+1 ... t+504 market sessions
no next-session Open = no_entry, do not roll to reopen
```

注意：当前产品 `src/labels.py` 的 bull 仍读未来 `high`，所以 candidate v2 与产品 H10/low60 的 High 口径是**有意不同**的；这是用户 H504 主任务，不把 H10 结果改名搬过来。

### 2.2 `session_clock.py`：独立市场日冷却

新增：

```python
dedupe_signals_market_calendar(signals, calendar=<independent market calendar>, cooldown=60)
```

约束：

- `calendar` 是独立 market-session clock，不从 signal dates 推导；
- exact boundary `distance == cooldown` 保留；59 抑制、60 保留；
- 信号日期不在 calendar 时抛错，禁止静默退化为 frame rank；
- per-stock cluster 边界保留；
- 不需要在测试里插 filler stock。

本轮决定性软件反例：同一股票两个信号实际相隔 108 sessions，旧 frame-rank 机制只看到两个唯一日期，保留 **1** 条；candidate session clock 保留 **2** 条。

### 2.3 `fold_support.py`：把“算术墙”限定到正确问题

新增闭式函数：

```text
minimum_dense_sessions_for_full_maturity_split(H) = 2H + 2
H=504 => 1010 sessions
```

证明口径只针对：dense candidates、至少一个 full-follow-up train candidate、dev 起点必须严格晚于 train deadline、dev 自身也必须在观察末端前完成完整 H follow-up。

新增 `fold_support_summary` 会明确输出：

```json
{
  "scope": "full_followup_bce_on_supplied_calendar_only",
  "does_not_imply_repository_or_local_history_absence": true
}
```

因此：当前仓库可见 886/887-session panel 若直接拿来做这个 H504 baseline，确实无法形成 full-maturity train→later mature dev；但这**不证明用户本机没有更早授权历史**，更不影响仓库当前 H10 矩阵能否训练。下一步必须先在本机真实授权数据上跑 inventory，而不是把 GitHub panel 时间跨度当成所有数据源的上限。

### 2.4 `feature_spec.py`：补齐 candidate 自己新增的泄漏列

上一候选虽然是显式 allow-list，但我本轮检查发现 candidate oracle 新增的字段里，至少以下几项没有进入 forbidden metadata 集：

```text
target_price
risk_floor
training_eligible
candidate_id
signal_date
```

其中 `target_price=4*entry_open` 与 `risk_floor=0.8*entry_open` 明确依赖 t+1 entry，本身就是决策时点未来信息；若手工 FeatureSpec 错把它们加入，会构成直接泄漏。

v2 已把这些以及 `code/date` 加入 fail-closed 禁止集合；仍然只有明确列在 `FeatureSpec.names` 且非 forbidden 的列能进模型。

### 2.6 新增真实本机迁移探针

新增 `compare_product_vs_session_oracle.py`，在本机真实 panel 上：

1. 计算 global market calendar；
2. 统计逐股 session gap；
3. 选 gap 最严重 16 股 + 无 gap 的稠密对照 16 股；

6. 跑 candidate market-session/Close H504 oracle；
7. 输出：
   - entry both-present mismatch；
   - product 有 entry 但 oracle `no_entry`；
   - 两者可比标签的 mismatch；
   - oracle outcome counts；
   - 每行对账 CSV。
