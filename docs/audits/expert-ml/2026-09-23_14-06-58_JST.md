## 1. 本轮结论

本轮新增登记：

`EML-P1-H504-ORACLE-METADATA-BARS-SCANNED-ALLOWLIST-BYPASS-001`

当前 H504 的 `FeatureSpec` 虽然宣称是“显式 feature allow-list”，并且已经禁止 `label_*`、`forward_*`、`entry_open`、`target_price`、`risk_floor`、`training_eligible_at` 等明显目标/未来字段，但它漏掉了 `label_h504_candidates()` 自己生成的两个 post-entry oracle 元数据：

- `bars_scanned`
- `first_missing_session`

其中 `bars_scanned` 是数值型，而且直接由 **t+1 之后的结果路径**计算。当前 `run_h504_hgb()` 会先把完整 H504 label ledger 与 feature frame 合并，再根据调用者传入的 `feature_cols` 在这个合并后的 `data` 上执行 `FeatureSpec.select(...)`。因此：

```text
FeatureSpec.from_names(["bars_scanned"])
```

当前不会报错；而 `data` 本身又确实含有这个 label-oracle 字段。也就是说，训练 API 的“禁止未来字段”门存在一个可达的显式绕过口。

这属于 **G1 / PIT feature contract 的 fail-open**。不过必须精确区分：当前 `run.py` 默认 T0 路径的 `feature_cols` 是从 `build_research_features()` 产出的 feature frame 枚举出来的，因此本轮没有证据表明现有默认 T0 已经自动吃进 `bars_scanned`；本问题证明的是 **训练 API 与 FeatureSpec 安全边界不完整**，不能据此把历史 T0 结果直接判成泄漏。

## 4. 风险分析

### 4.1 为什么 `bars_scanned` 比普通 metadata 更危险

它不是一个无害 ID，而是结果路径的数值摘要。

- timeout 候选在完整 H504 随访时通常取 H；
- 早 success / risk 在事件发生时停止扫描，值通常更小；
- unknown 也可在首次缺失处停止。

因此这个字段天然携带 outcome timing 信息。即使它不完美等价于标签，也属于严格禁止进入 t 时刻特征集的未来 oracle。

### 4.2 当前默认 T0 的边界

当前 `run.py` 的默认 T0 feature list 来自 `build_research_features()`，而不是从合并后的 `data` 全列自动挑选，因此本轮 **没有证据证明默认 T0 当前已经使用 `bars_scanned`**。

所以本问题的正确状态是：

- `CURRENT_DEFAULT_T0_AUTO_LEAK = NOT_SHOWN`
- `TRAINING_API_GUARD_FAIL_OPEN = CONFIRMED`
- `PLANNED_T1_T5_MLP_TCN_MUST_NOT_REUSE_THIS_WEAK_BOUNDARY = REQUIRED`

这也是为什么应在 T1–T5、H504 MLP/TCN 继续扩展之前修，而不是等出现异常漂亮的分数以后再追溯。

## 5. 建议修复

只给 `_FORBIDDEN_EXACT` 再补两个名字可以止血，但更稳健的修法应同时做结构隔离。

### P1-a：补 canonical oracle field set

在一个单一来源中维护 H504 oracle/output schema，例如：

```text
H504_ORACLE_FIELDS = {
  entry_open, entry_session, deadline, label_end,
  target_price, risk_floor, terminal_session,
  label_known_at, training_eligible_at, training_eligible,
  outcome_class, label_joint, label_resolved,
  bars_scanned, first_missing_session, ...
}
```

`FeatureSpec` 直接引用它，避免 task oracle 增列后忘记同步 blacklist。

### P1-b：训练前先验证 feature source，再与 labels 合并

`run_h504_hgb()` 应先证明：

```text
set(feature_cols) ⊆ feature_frame_schema
```

然后只取这些 feature 列再与 label ledger 合并，而不是把完整 label ledger 与完整 feature frame 合并后再依赖 blacklist 保护。

这能把安全边界从“记得禁止所有未来列”升级为“模型只能看到被 feature pipeline 正式产出的列”。

### P1-c：把 feature source/schema 写进模型签名

当前另有已发表问题 `EML-P1-H504-SIGNATURE-BLIND-TO-FEATURE-SOURCE`。本轮修复应与它合并：模型签名至少绑定 feature schema/version/source hash，避免同名特征由不同实现产生却复用旧 COMPLETE。
