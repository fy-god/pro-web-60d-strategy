## 2. 新 P1：10800 秒目标只被记录，不参与成功退出判定

**ID：`EML-P1-H504-TARGET-ACTIVE-NOT-ENFORCED-AT-EXIT`**

### 2.1 Receipt 会计算 `target_met`，但只是写字段

文件：`src/ml/research_h504/receipts.py`

当前 `ResearchSessionReceipt.finalize()` 会计算：

```python
effective = sum(v for k, v in phase_seconds.items() if k not in excluded)
...
'target_met': effective >= self.target_active_seconds,
```

并将 `target_met` 写入 `execution_receipt.json`。但 `finalize()` 本身没有任何 fail-closed 语义：它不会因为 `target_met=false` 改变调用方退出码，也不会要求 READY/INTERRUPTED 队列继续执行。

这一点单独看只是“receipt 被动记账”；决定性问题在下一层。

### 2.2 `run.py --stage all` 在 `target_met=false` 时仍固定 `return 0`

文件：`src/ml/research_h504/run.py`

当前收尾逻辑是：

```python
if interrupted:
    status='INTERRUPTED_WALL_BUDGET'
elif any(str(r.get('status','')).startswith('COMPLETE') or r.get('status')=='REUSED_COMPLETE' for r in results):
    status='COMPLETED_AVAILABLE_RESEARCH_NOT_CERTIFIED'
else:
    status='BLOCKED_NO_FIT'
...
if receipt:
    receipt.finalize(
        stop_reason='WALL_BUDGET_REACHED' if interrupted else 'QUEUE_DRAINED_OR_BLOCKED',
        result_status=status,
        ...
    )
print(...)
return 0
```

这里**没有**读取 `execution_receipt.target_met`，也没有：

- `effective_seconds < 10800 && READY -> EARLY_STOP_WITH_READY_WORK`
- `effective_seconds < 10800 && INTERRUPTED -> continue/resume`
- `effective_seconds < 10800 && true hard block -> MIN_RUNTIME_NOT_MET + exact blocker`

所以一个几分钟完成的 `--stage all` 可以写出 `target_met=false`，同时整个 CLI 仍返回 0。

### 2.3 更硬证据：仓库自己的测试把这种行为锁成“正确”

文件：`tests/research_h504/test_candidate.py`，测试：`test_all_stage_writes_start_and_execution_receipts`

当前测试明确要求：

```python
assert main([
    '--stage','all',
    ...,
    '--target-active-seconds','10800',
    '--normal-wall-limit-seconds','12600',
    '--hard-runner-timeout-seconds','13200'
]) == 0
...
assert end['target_met'] is False
```

也就是说，现有测试不是“没覆盖三小时门”；它更强：**它主动规定 10800 秒没达到也应返回成功。**

这与 v5 合同直接冲突。v5 要求：少于 10800 有合法 READY 工作时记 `EARLY_STOP_WITH_READY_WORK`，不能把上限或短运行冒充三小时完成；`target_met=false` 明确就是未达三小时。

因此该缺陷不是文档措辞问题，而是**控制流＋测试合同共同把错误语义固定住**。

### 2.4 外层 launcher 又把 child rc=0 当成成功，形成第二层放大

文件：`scripts/run_fixup.py`

launcher 的提示词已经写得很明确：

> “继续未完成的真实研究队列，目标单次三小时”

而 `scripts/fixup_prompt.txt` 进一步明确：

> `execution_receipt里target_met=false就是未达三小时；agent退出码0不表示训练成功。`

但是 launcher 实际收尾只做：

```python
rc = process.wait(...)
...
print({
    'agent_exit_code': rc,
    'training_status': 'READ_RESEARCH_EXECUTION_RECEIPT'
})
return 0 if rc == 0 else 1
```

它**并没有真的读取、定位、验证任何 `execution_receipt.json`**。`training_status='READ_RESEARCH_EXECUTION_RECEIPT'` 只是提示文字，不是校验动作。

因此现在存在完整链条：

```text
研究 runner 提前结束
  -> execution_receipt.target_met=false
  -> run.py 仍 return 0
  -> 本地 agent 可 rc=0
  -> run_fixup.py 只看 rc=0
  -> launcher 最终也 return 0
```

这意味着：**即使 Windows 任务以后正确注册到 PT3H50M，单次三小时仍然不能由现有退出链保证。**

### 2.5 影响

这会直接破坏用户要求的“单次连续三小时真实研究”验收：

1. 任务可能有 10800 秒以上的外层可用时间，但内部队列做完一小项就提前退出；
2. `target_met=false` 虽被写入 receipt，却不改变程序成功状态；
3. 调度层只看到 rc=0 时可能误以为本轮已经完成；
4. 下一触发又开一个新 session，形成用户明确禁止的“多次短运行累计冒充三小时”。

这和之前的 `PT2H30M / 未注册任务` 不同：

- **runtime config 缺陷**决定“最多能活多久”；
- **本 P1** 决定“即使能活足够久，会不会被允许提前成功退出”。

两个都必须修。

## 4. 本轮隔离候选：单 session 退出分类＋launcher receipt handoff

本轮在隔离沙箱写了一个**窄候选 guard**，不改产品源码，不计市场 fit。

候选行为：

```text
effective >= target
    -> TARGET_ACTIVE_SECONDS_MET / exit 0

effective < target AND READY work exists
    -> EARLY_STOP_WITH_READY_WORK / nonzero

effective < target AND runtime/safety/permission/resource hard block
    -> MIN_RUNTIME_NOT_MET + exact blocker

effective < target AND queue state cannot be proven
    -> MIN_RUNTIME_NOT_MET + QUEUE_STATE_UNPROVEN / nonzero

launcher:
    target_met=true -> accept
    explicit hard block -> accept as blocked, NOT as 3h success
    target_met=false + QUEUE_DRAINED_OR_BLOCKED -> reject
```

沙箱候选测试：**7 passed in 0.06s**。

其中专门有一条测试锁住本轮发现：

```python
ok, why = validate_launcher_handoff({
    'target_met': False,
    'stop_reason': 'QUEUE_DRAINED_OR_BLOCKED'
})
assert not ok
```

### 建议接入点

1. `run.py` 保存显式 queue snapshot：`READY / INTERRUPTED / NEEDS_IMPLEMENTATION / BLOCKED / COMPLETE`。
2. `ResearchSessionReceipt.finalize()` 后，由 runner 用 `effective_seconds + queue state` 决定退出码。
3. 当前 smoke test 不应继续写“10800目标 + 几秒执行 + rc=0”为正确；软件 smoke 应显式传 `--target-active-seconds 0`，把“功能 smoke”与“三小时生产合同”分开。
4. `run_fixup.py` 必须读取本轮 agent 产生的 handoff（至少指向唯一 final execution receipt），并验证：
   - `target_met=true`；或
   - 明确 hard blocker / all-valuable-work-exhausted，且状态为 `MIN_RUNTIME_NOT_MET`；
   - 不能只看 child rc。
5. 加变异测试：把 under-target 分支改成成功，测试必须红。

候选 ZIP 只作为对话内临时交付，不是 GitHub 项目证据，也不等于产品已修。

## 7. 下一次本地接入的硬顺序

在真正启动第一轮可验收的 3h session 前，优先级应为：

1. **一次性恢复/注册现有 `ProWeb60d-Fixup` 任务**，只改本任务运行上限与 prompt，保留原 trigger/action/principal；先导出前态，再核对后态；`ExecutionTimeLimit >= PT3H50M`。
2. 把本轮 **target enforcement** 接入 runner + launcher；`target_met=false + READY` 必须 `EARLY_STOP_WITH_READY_WORK`，不能 rc=0 被当成功。
3. training-capable direct stage 接 receipt/锁/fit-budget，或 REAL_MARKET 下 fail closed 到 `--stage all`。
4. 落地已有高优先级门禁：shared lock、measured provenance、artifact COMPLETE hash 验证、resolved-dev 支持、跨 session 48-fit 原子台账、feature-source signature、price-basis gate。
5. 补对应**变异必红**测试，不能再只靠当前 65 项全绿。
6. 之后才进入真实：`candidate_manifest -> H504 outcome -> candidate-aware fold_support`。
7. 有合法 H504 fold：继续 T0→T3/T1–T5 主线；无合法 fold：明确 `BLOCKED_PROTOCOL_H504`，同一 session 执行 `AUX_REAL_HISTORY` base-vs-plus，但绝不把 AUX 数字当 H504 成绩。
8. 达到 10800 effective seconds 后保存并正常退出；若早于目标因 hard blocker 停止，receipt 必须写 `MIN_RUNTIME_NOT_MET` + 精确原因。
