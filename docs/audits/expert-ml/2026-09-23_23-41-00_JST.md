## 2.【新发现 · 已确认错误】`EML-P2-EVIDENCE-TYPE-NOT-IN-REUSE-SIGNATURE-002`

### 2.1 缺陷（文件/函数/行）

`src/ml/research_h504/run.py:150`（H504 T0）与 `:173`（AUX-TCN）构造复用签名时，**键集合里没有 `evidence_type`**。我用 **AST**（不是正则）读出全部键：

```text

run.py:173  keys = pipeline_hash, calendar_hash, task, rep, seed, data, features, epochs, patience, batch_size

AST 正控：我已知必然存在的键 'pipeline_hash' 被找到 = True（否则该探针作废）
```

`src/ml/research_h504/registry.py:19-23`：

```python
def latest_complete(self, signature):
    for r in reversed(self.rows()):
        if r.get('signature')==signature and str(r.get('status','')).startswith('COMPLETE'):
            return r
    return None
```

**只比对签名与状态前缀，完全不看 `evidence_type`**。`evidence_type` 在 `run.py` 只用于 `:88/:90` 的当前运行自检与 `:155/:181/:190` 的写入，**从不参与复用匹配**；`registry.py` 中 `evidence_type` 出现 **0** 次。

### 2.2 触发条件 / 反例（我实跑）

```text
RUN 2  --evidence-type SYNTHETIC   -> 写入 registry 行 evidence_type=SYNTHETIC status=COMPLETE_H504_DEV

       rc=0
       result: H504_JOINT/T0 status=REUSED_COMPLETE      <-- 复用第 2 步那行
       run_summary.evidence_type    = REAL_MARKET         <-- 当前运行的标签
       execution_receipt.evidence_type = REAL_MARKET
       registry rows = 1（仍是 SYNTHETIC，未被改写）
       NEW fits = 0
```

⇒ **一个软件样本（`SYNTHETIC`）的已完成 fit，被一个 `REAL_MARKET` 运行当作自己的结果复用并如实写进当前运行的 `run_summary.json` / `execution_receipt.json`。** 这直接触碰手册要求的三轴分离：**软件样本与实股证据被混在同一份「本轮结果」里**。

负控（证明签名确有区分力、不是恒真）：

```text
RUN 4  同一 --out，换成不同 panel（close×1.37）
       result status = COMPLETE_H504_DEV（不是 REUSED_COMPLETE）
       REUSED 计数 = 0
```

另有独立负控在 §2.1 的 AST 臂与 `registry` 行为臂：我用仓库**自身** `Registry` 类写入一行 `SYNTHETIC + COMPLETE` 再调用 `latest_complete(sig)` -> **命中**；写入同签名但 `BLOCKED_NO_FIT` 的行 -> **返回 None**。⇒ 该探针不是「对任何输入都返回真」。

### 2.3 机制

复用键 = 数据/管线/特征/模型配置的纯函数。**同一份 panel 与同一份候选，无论运行自称 `SYNTHETIC`、`UNSPECIFIED` 还是 `REAL_MARKET`，签名完全相同**（我用 `stable_hash` 实测四种标签得到**同一个**签名：`4699dca51af28be1…`）。而 `--evidence-type` 默认值是 `UNSPECIFIED`（`run.py:72`），所以**最可能的触发路径是默认值**：一次忘了带该参数的运行写下一行 `UNSPECIFIED + COMPLETE`，之后一次**正确标注** `REAL_MARKET` 的运行会静默复用它。

### 2.4 影响（我明确限定，不夸大）

- **会被影响**：`run_summary.json` 顶层 `evidence_type`、`execution_receipt.json` 的 `evidence_type` 与 `real_train_seconds`（后者会是 0），以及**任何只看这两份文件的下游读者**。
- **不会被改写**：registry 里那行原始记录的 `evidence_type` 保持 `SYNTHETIC` 不变；复用产生的 result 条目里**没有** `evidence_type` 字段。所以这**不是伪造数字**，而是**证据类型的可追溯性泄漏**。
- **但结论确实变了**：因为 `REUSED_COMPLETE` 会喂给 `run.py:186` 的成功判定，一个**零新增 fit**的运行会被报成 `COMPLETED_AVAILABLE_RESEARCH_NOT_CERTIFIED`，而不是 `BLOCKED_NO_FIT`。
- **可达性我如实评价为「真实、有条件、多数是自己造成的」**：需要 `--out` 相同且 panel/候选/日历/管线字节一致。跨两个真正不同的数据集**不会**发生（数据变了签名就变，RUN 4 已证）。**我另需披露一个探针缺陷**：RUN 3 里我把 `calendar.csv` 直接写成 panel 的 `bdate_range`，从而**人为保证了 `calendar_hash` 相同**；真实 A 股日历若有假日缺口，`prepare_panel` 会把日历裁到 panel 跨度（`data_io.py:34` 附近），`calendar_hash` 可能不同而**阻断**复用。所以精确表述是：**「同一批输入 + 变更或省略证据标签 + 同一个输出目录」**，而不是跨研究洗白。
- **真实市场影响**：**无**。本轮 `outputs/` 类产物均未入库（我确认 `experiment_registry.jsonl` / `run_summary.json` / `execution_receipt.json` 在 `origin/main` 中**均未 tracked**），因此我**没有**真实 A 股上的实例，只有受控软件样本上的反例。

把 `'evidence_type': args.evidence_type` 加进 `run.py:150` 与 `:173` 两个签名字典；或让 `latest_complete` 接受并匹配证据类型。**一行级修复**，但要在 `REUSED_COMPLETE` 的 result 条目里同时回写被复用行的 `evidence_type`，否则可追溯性仍然丢失。

`finalize()`（`receipts.py:154-189`）**只计算并写入** `target_met`，**没有任何 fail-closed 语义**。因此：**9000 s 上限 < 要求 13800 s**，且 launcher 只看子进程 rc。这与「五分钟成功退出」是**同一根因的两个面**。**仓库模板不能证明用户机器上真实注册任务的值**，故：

```text
LOCAL_RUNTIME_APPLIED = NOT_VERIFIED / LOCAL_APPLY_PENDING
LOCAL_SINGLE_CONTINUOUS_3H_COMPLETED = NOT_VERIFIED
```
