## 1. 新 P1：已知 `Low` 已跌破 0.8E，但同日 `Close` 缺失时，标签器错误返回 unknown

**新 ID**：`EML-P1-H504-RISK-KNOWN-BUT-CLOSE-MISSING-MISCLASSIFIED-UNKNOWN-001`

### 1.1 合同要求

H504 合同是：

- t 日收盘发信号；
- t+1 有效 Open = `E`，不可入场不顺延；
- t+1..t+504：若某日 `Low < 0.8E`，该候选已经触发 risk；
- 若同日还 `Close > 4E`，仍然 **risk 优先**；
- `Close` 只用于 success，risk 的充分价格字段是 `Low`。

`H504TaskSpec` 自己也显式声明：`risk_field='low'`、`target_field='close'`、`risk_priority_same_session=True`。

### 1.2 当前实现为什么错

当前 `label_h504_candidates()` 对每个 post-entry session 做：

```python
valid = np.isfinite(low) & (low > 0) & np.isfinite(close) & (close > 0)
risk = valid & (low < floor)
goal = valid & (close > target)
event = np.flatnonzero((~valid) | risk | goal)
```

这把 **risk 可知性错误地依赖到了 Close 是否存在**。

当：

- `Low` 有效且 `< floor`，所以风险已经确定；
- 但同日 `Close = NaN`；

则 `valid=False`，进而 `risk=False`，随后 `(~valid)` 先把该 session 送入：

```text
outcome_class = unknown_missing_price
label_joint = NaN
label_resolved = False
```

这违背了 risk-first 合同。缺的是 success 所需的 Close，不是 risk 所需的 Low。

### 1.3 本轮独立最小反例

本轮在隔离沙箱按当前产品逻辑构造：

```text
signal day = day 0
entry day  = day 1
E          = 10
risk floor = 8
post-entry day 1 Low   = 7.5
post-entry day 1 Close = NaN
calendar   = 510 个连续 business-day session
```

**当前实现输出**：

```text
outcome_class         = unknown_missing_price
label_joint           = NaN
label_resolved        = False
first_missing_session = day 1
label_known_at        = day 1
```

**按任务合同应输出**：

```text
outcome_class  = risk
label_joint    = 0
label_resolved = True
terminal_session = day 1
```

因为 `Low=7.5 < 8` 已足以确定 risk；Close 缺失不能把已知 risk 改回 unknown。

### 1.4 影响不是“只少一个状态字符串”

该错误会把一部分**已知负例**从 resolved 集合中拿掉：

- `run_h504_hgb()` 的 dev 指标只在 `label_joint.notna()` 的 resolved 行上计算；
- fold / support / base-rate 分析又依赖 resolved 与 training-eligible 支持；
- 因此若真实数据存在“Low 完整、Close 缺失”的 risk-breach session，当前逻辑可能同时：
  1. 降低 resolved 支持；
  2. 把已知 risk 负例移出指标分母；
  3. 改变 base rate / Brier / log-loss / AP 的样本集合；
  4. 在本来接近支持门槛的折上改变 READY/BLOCKED 判断。

本轮**不声称真实 A 股 panel 中该形态出现了多少次**，因为没有用户本机数据执行通道。本轮确认的是：**只要该形态出现，当前 oracle 必然错误分类。**

另一个从属症状是 `bars_scanned = j + int(valid[j])`：若风险发生在第一 post-entry session 且 Close 缺失，当前结果甚至记录 `bars_scanned=0`。修正 risk 可知性后，该 session 应计为已扫描 1 个 session。

现有 `tests/research_h504/test_candidate.py` 已覆盖：

但没有覆盖这个关键不对称场景：

```text

```

所以当前测试“risk priority same day”只证明 **Low/Close 都完整时** 的优先级，没有证明 **risk 的可知性只依赖 Low**。

## 3. 窄修复候选与本轮沙箱验证

本轮没有远端改产品源码，只做了窄候选。核心应该把 low/close 的 observability 拆开：

```python
low_valid = np.isfinite(low) & (low > 0)
close_valid = np.isfinite(close) & (close > 0)

risk = low_valid & (low < floor)
goal = low_valid & close_valid & (~risk) & (close > target)
unknown = (~risk) & ((~low_valid) | (~close_valid))
event = np.flatnonzero(risk | unknown | goal)
```

在命中 session 上严格按：

```text
risk -> unknown -> success
```

分类。这样：

1. `Low < floor, Close=NaN` => `risk`；
2. `Low >= floor, Close=NaN` => `unknown_missing_price`；
3. `Low=NaN, Close>target` => `unknown_missing_price`，因为不能排除同日 risk；
4. `Low < floor, Close>target` => `risk`；
5. 正常无 risk、Close>target => `success`。

隔离候选测试：**5 passed in 0.05s**。

候选 ZIP SHA-256：

```text
5cd05d6a73ca558263829497caf36e2595ba0d5f3fce11985dfca53c04418d87
```

报告不依赖该 ZIP 才能理解修复；完整规则、测试输入和预期均已写在本报告。

### 必须补的 mutation test
