# 2. P0 / P1 错误与风险状态

## EML-P0-COOLDOWN-GRID：60-session cooldown 仍然不按市场交易日计数【未修】

**文件 / 函数：** `src/labels.py::dedupe_signals()`。

当前代码仍然是：

```python
session_index = {d: i for i, d in enumerate(sorted(out["date"].unique()))}
positions = out["date"].map(session_index).to_numpy()
```

`out` 是 signal frame，因此这里数的是“全体信号出现过的日期”，不是 exchange sessions。若同一股票在真实 market session 0 和 60 都有信号，但全市场中间只有少数日期出现任何信号，当前 `positions` 距离会远小于 60，第二条会被错误压掉；给别的股票增加中间信号又可能改变目标股票的 cooldown 结果。

### 影响

- deduped signal 数和 event recall 不稳定；
- 市场平静期 cooldown 被人为拉长；
- 同一只股票的发布策略依赖无关股票是否触发信号，不满足 per-code causal state machine。

### 修复

在 panel/ledger 层先固定独立交易所 `market_session_id`，信号行只携带该 id，`dedupe_signals()` 禁止自己从信号子集重建时钟：

```python
if "market_session_id" not in signals:
    raise ValueError("market_session_id required")
```

更推荐把 cooldown 移到 immutable signal ledger 的发布状态机，而不是作为事后统计函数。

### 验收

1. day0/day60，期间没有其他股票信号，day60 必须保留；
2. 增删其他股票中间信号，目标股票结果不变；
3. 59 suppress / 60 keep；
4. 停牌股自身没有 bar 时 market clock 仍按交易所 session 前进。

## EML-P0-LEDGER-ORDER：`score_signals()` 仍然“先看未来是否 resolved，再决定第一事件”【本轮深化确认】

上一轮主要在 low-zone 路径指出 future-resolved 反向筛候选。本轮继续检查发现，**通用 Web Pro 计分函数也有同一结构问题**。

**文件 / 函数：** `src/labels.py::score_signals()`。

当前顺序：

```python
live = signals[signals["label_resolved"]].copy()
...
deduped = dedupe_signals(live, cooldown=cooldown)
```

这意味着一个 t1 信号如果未来结果窗口不完整，会先被删除；同股 cooldown 内 t2 信号若未来完整，则可能被当成“第一事件”。真实在线系统在 t1 当天根本不知道 10/60/504 个未来 session 以后是否能完整观察，它已经决定是否发布；如果 t1 已发布，t2 应该由当时的 cooldown state 决定，而不能因为 t1 后来 censored 就复活。

### 最小反例

```text
同股：t1=100 发信号，未来未完整 -> label_resolved=False
t2=120 再发信号，未来完整 -> label_resolved=True
cooldown=60
```

因果发布：t1 先发布，t2 在 60-session 内应 suppress；结果关联阶段把 t1 标 censored/unresolved。

当前评价：先删除 t1，再让 t2 成为 deduped event。于是“未来能否完整观察”改变了历史发布轨迹。

### 影响

- `bull_precision_deduped` / `joint_precision_deduped` 的事件分母不是自然在线发布分母；
- right-censoring 与 signal policy 混在一起；
- 长 H504 尤其严重，因为尾部和退市/数据缺口更常 censored。

### 修复

```text
causal candidates -> score -> threshold -> market-session cooldown -> immutable signal_id
                                                |
                                                v
                                   后续再 join outcome ledger
```

发布账本先冻结，再分：`resolved_goal / resolved_risk / timeout / censored / data_unknown`。精确率可以在 resolved event 上报告，但必须同时报告 `published_total`、`resolved_published`、`censored_published`，且 censored 不允许改变过去的 signal_id。

### 验收

构造同一批 causal scores，只改变未来 outcome 完整性；**发布 signal_id 集合必须完全不变**。改变 outcome 只允许改变 evaluation status。

## EML-P0-H504-HIGH-CLOSE：仓库 `low504` 仍不是用户当前 H504 主目标【本轮明确任务级错误】

**文件：** `src/labels.py`。

仓库把：

```python
REGIMES["low504"] = (504, 3.00, 0.80)
```

传给同一个 `forward_outcomes()`，而这个函数的 bull 与 first-hit 都使用 `high`：

```python
highs = out["high"].to_numpy(...)
...
newly = ... & (high_d > target)
...
bull = forward_high > target
```

也就是说，`low504` 的“4x”是**未来某日 intraday High 严格超过 4E**，不是当前工作口径要求的**某日 Close 严格超过 4E**。

这不是一个小阈值差异。某股盘中冲到 4.1E、收盘只有 3.6E，在仓库 `low504` 会成为 bull；在当前 H504 主目标下不是。

### 影响

- 任何 `low504` base rate、低位联合精度、专家排序都不能直接作为用户当前 H504 目标的成绩；
- H10 `label_high` 可以继续作为短期研究任务，但不能被重命名或迁移为长期 close4x 结果；
- KDJ、position 等特征在 “盘中冲高” 和 “收盘站上” 两个任务中的贡献可能完全不同，不能直接沿用 H10/High 消融结论。

### 修复

建立真正的 `TaskSpec`，至少固定：

```text
entry_price      = open at market_session[t+1]
goal_price_field = close
goal_operator    = >
goal_multiple    = 4.0
risk_price_field = low
risk_operator    = < 0.8E
horizon_sessions = 504
tie_priority     = risk
```

标签器按市场日逐日推进。每个 d 先检查当天 risk，再检查 `close_d > 4E`；同日二者都成立时直接 risk-first。

### 能证伪的实验 X13

在**同一候选队列、同一 E、同一 504 market sessions**上同时计算：

- A：现有 `max(high)>4E`；
- B：目标 `first(close>4E)`；

输出：正例重叠、`A-only`、`B-only`、goal-day 差异、joint label flip、base rate 变化。只有完成这张 parity 表之后，才允许讨论 H504 专家/ML 性能。

## EML-P0-SESSION-ALIGN：next stock row 仍不等于 next market session【未修】

`forward_outcomes()` 的 entry 仍通过同一 code 的下一行取得：

```python
entry[:-1] = opens[1:]
same_next[:-1] = codes[1:] == codes[:-1]
```

未来 H 也按该股票后续行推进。停牌或缺 bar 时，这会把几天后的复牌 open 当“下一市场日开盘”，并可能把 H504 拉长成 504 根个股 bar。

**修法：**独立 exchange calendar；`entry_session=t+1` 若该股无可成交 open，则 `entry_unavailable`，禁止滑到复牌日；future horizon 用 market-session id，不用 stock-row offset。

## EML-P1-CALIB-TRAIN：RF/HGB 的发布阈值仍取自拟合数据本身【未修】

**文件 / 函数：** `src/ml/walkforward.py::evaluate_fold()`。

当前：

```python
model.fit(x_tr, y_tr)
s_tr = model.predict_proba(x_tr)[:, 1]
s_te = model.predict_proba(x_te)[:, 1]
thr = pick_threshold(s_tr, y_tr, cfg.target_rate)
```

这不是 test-label leakage，但阈值是在**模型刚拟合过的同一训练样本分数**上取 top 2% 分位数。若模型训练分数比未来分数更极端，固定阈值到 OOS 后发布率会漂移。现有 RF 四折 signal 数 `11210 / 7365 / 1545 / 2747` 已经提示 policy transfer 并不稳定。

### 改进

每个 outer fold 内拆成：

```text
fit block -> purge -> temporal calibration block -> freeze threshold -> outer test
```

更稳健的版本是用 inner expanding folds 生成 train OOF scores，再从 OOF score 分布冻结 threshold；禁止用 fitted-in-sample scores。

### 验收

比较原 policy 与 temporal-OOF policy：

- pooled OOS precision 与 clustered LCB；
- 每折 publication share 的 CV / max-min ratio；
- signals、hits、distinct stocks、distinct dates；
- calibration curve / Brier；
- 不能只因为信号更少就宣布更优。

若 OOF threshold 没改善稳定性且 precision LCB 下降，则淘汰，不继续增加校准复杂度。

## EML-P1-AUDIT-PUSH-SCOPE：新重试逻辑可能把无关本地 commit 一起推到 main【本轮新增运维风险】

`commit_and_push()` 现在先 commit `reports/AUDIT_STATUS.md`，然后：

```python
git push origin HEAD:main
# 失败后
git fetch origin main
git rebase --autostash origin/main
git push origin HEAD:main
```

代码注释假设“our single status commit”，但函数**没有验证这个假设**：没有检查当前分支、没有检查 `HEAD..origin/main` / `origin/main..HEAD` 的 commit 集，也没有断言本地 ahead commit 只修改 `reports/AUDIT_STATUS.md`。

如果人工工作在同一 checkout 上已经有一个尚未 push 的代码 commit，定时审计随后再提交 status，`HEAD:main` 可能把**两个 commit 一起推上去**。`--autostash` 只保护未提交工作树，不限制历史提交范围。

### 修复

最佳方案仍是独立 worktree/独立 automation branch。最小防线：

1. audit 前断言当前 `HEAD == origin/main`；
2. 若不等，拒绝自动 push，记录 `LOCAL_AHEAD_BLOCKED`；
3. status 生成后断言 `git rev-list --count origin/main..HEAD == 1`；
4. 断言该唯一 commit 的 changed paths 只有 `reports/AUDIT_STATUS.md`；
5. 再 push；遇 race 时重新基于 fresh `origin/main` 生成新的 status commit，而不是 rebase 任意本地历史。

这不是模型精度问题，但它直接关系到自动审计能否安全地作为证据发布器。

# 4. 本轮待验证新点子

以下都是研究假设，不是已证明有效策略。

## IDEA-EML-07：Cross-feature residualization，而不是“全加”或“全删”

### 依据

当前 dense H10 ablation：`drop-cross=18.53%` 高于 `all=16.44%`，说明原始 cross features 在现有 HGB 中可能带来冗余、相位噪声或与 absolute momentum/position 重复；但这并不能证明相对强弱信息本身无用。

### 方法

对每个 cross feature `z_cs`，只用 training block 拟合其可被 absolute / market state 解释的部分：

```text
z_cs = beta0 + beta_abs * X_abs + beta_mkt * R_t + epsilon
z_resid = z_cs - z_hat
```

test/holdout 只应用训练期 beta。模型使用 `z_resid`，而不是原始 rank/z-score。

### 对照

- A：drop-cross；
- B：raw cross；
- C：residualized cross。

### 验收 / 淘汰

C 相对 A 至少在 3/4 outer folds 同方向改善 precision 或 event-recall，同时 publication share 不出现更剧烈漂移；否则认为 cross residual 没有可迁移增量，删掉，不继续堆交互项。

### 风险

若 cross feature 本身就是 absolute feature 的确定变换，residual 可能只剩噪声；这是该实验应当允许出现的失败结果。

## IDEA-EML-08：OOF path-risk signature，把 H10 变成 H504 辅助状态，而不是目标替代

### 机制

单一 `P(+30% high in H10)` 太偏向冲高。对每个 t 用过去数据 OOF 训练两到三个短期辅助头：

- `p_up30_H10`：10日内 high +30%；
- `p_dd20_H10`：10日内 low < 0.8E；
- 可选 `p_close_strength_H20`：20日内 close 达某较低阶段阈值。

组成：

```text
path_signature = [p_up30_H10, p_dd20_H10,
                  p_up30_H10 - lambda * p_dd20_H10]
```

这些 score 必须是 inner-time OOF 或此前冻结模型对 later data 的预测，不能用同样本 fitted score。

### 为什么可能有用

主任务是“长周期巨大上涨 + 先不破风险线”。短期爆发概率和短期下破概率分别描述动力与脆弱性，比单一 H10 bull 更贴近 competing-path 结构，同时不改变最终 H504 标签。

### 对照

H504 base model vs `+ p_up30` vs `+ p_dd20` vs `+ full signature`，同候选、同 ledger、同 outer time split。

### 淘汰

若 full signature 不能在至少 3 个时间块中改善 H504 joint precision LCB / event recall，或增益只来自单一短期热门年份，则删除，不把 H10 成绩包装成长周期证据。

## IDEA-EML-09：Causal cluster-normalized training，减少同一低位事件被连续日样本重复加权

### 问题

训练矩阵按 stock-day 行学习；一个股票在同一低位阶段连续几十天都满足类似条件时，这一“事件”会贡献几十条高度相关样本。评价又希望按 first-signal / cooldown 看事件级表现，训练目标和评价单位不一致。

### 方法

仅根据**当时可知候选状态和 market-session 距离**构造 candidate cluster，不使用未来 outcome。对 cluster c 中的 n 条训练行赋：

```text
w_i = 1 / n_c
```

或每个 epoch 从每个 causal cluster 抽固定数量日期。这样保留自然候选分布用于评价，但训练时避免一个长低位阶段支配梯度。

### 对照

- A：原始 row-unweighted；
- B：cluster-normalized weights；
- C：每 cluster 1-row stochastic sample。

### 验收 / 淘汰

在事件级 H504 指标上 B/C 至少一个相对 A 提升，同时 distinct-stock 覆盖不下降、市场时间簇 LCB 不恶化；若只提升行级 AUC 而 event precision/recall 不变，则淘汰。

### 关键限制

cluster 绝不能按“未来是否成功/何时成功”定义，否则又把 outcome 泄漏回采样。
