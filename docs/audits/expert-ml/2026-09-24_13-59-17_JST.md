## 2. 新 P1：H504 现在没有命中率 policy，`COMPLETE_H504_DEV` 不能回答 50%

### 2.1 当前 `train_h504.py` 到底输出什么

当前 `src/ml/research_h504/train_h504.py` 的 HGB 流程：

1. 生成 H504 label ledger；
2. 合并 signal-date features；
3. 找第一个合法 train→dev split；
4. HGB 拟合；
5. 对整个 dev 输出 `score=p`；
6. 对 resolved dev 只算：
   - `logloss`
   - `brier`
   - `average_precision`
7. 保存 `model.pkl` 与 `dev_predictions.csv`；
8. 返回 `status='COMPLETE_H504_DEV'`。

当前 `metrics` 字典明确没有：

```text
threshold
signals
tp
fp
precision
recall
publication_rate
TARGET50_REACHED
TARGET70_REACHED
```

`average_precision` 是 ranking/PR 曲线面积型指标，**不是**某个实际出信号 policy 的命中率。

### 2.2 `run.py` 也没有补上这一层

当前 `run.py --stage h504-hgb` 直接：

```text
run_h504_hgb(...)
print(res)
return 0
```

`--stage all` 的 H504 T0 也只是把 `run_h504_hgb()` 的结果写进 registry。没有：

- calibration block；
- threshold fitting；
- fixed signal budget；
- dev 前冻结 policy；
- TP/signals/precision/recall 复算；
- 50% / 70% target gate。

所以即便下一次真实 H504 T0 真跑完了，现有代码仍最多告诉我们：AP/Brier/log-loss 是多少；**不能自动回答“命中率有没有 50%”。**

### 2.3 这为什么不是“少记一个指标”

如果只是在 `dev_predictions.csv` 上事后扫阈值，然后挑出 precision 最大的那个阈值，会出现三层偏差：

1. **同一 dev 同时用于模型比较和 policy 选择**；
2. 扫多个 threshold / signal count 后只报最大值，带来 multiple-selection bias；
3. 极少信号可以轻易制造 50%/70% 甚至 100% 的表面 precision。

仓库旧 H10 文档自己已经证明了这个陷阱：单一 fitted ranking 在极小发布量可以出现很高 precision，但一旦要求有用信号数，真实 OOS frontier 明显下降。因此 H504 不能再复刻“先看 dev，再挑最好 threshold”的老错误。

**结论：H504 的“模型 score 学习”与“发布 policy 学习”必须拆成两个时间阶段。**

## 3. 正确协议：train → calibration → untouched dev

### 3.1 三段职责必须分开

建议增加一个独立 publication-policy 层：

```text
train block
  └─ 只拟合模型参数 / 预处理 / feature selection

calibration block
  └─ 只选择发布 operating point
     例如预注册 k ∈ {50,100,250,500,1000}
     或预注册 score/rank budget

untouched dev block
  └─ 冻结 policy 后一次性评价
     TP / signals / precision / recall / base rate / lift
     AP / Brier / log-loss 仍保留作为概率质量指标
```

不能让 dev 的 label 反向改变 calibration threshold。

### 3.2 50% 目标必须附带最小支持

`TARGET50_REACHED` 不能由以下情况触发：

```text
1/1 = 100%
7/10 = 70%
26/50 = 52% 但 threshold 是看完 dev 后选的
```

建议 policy spec 至少固定：

```text
target_precision = 0.50 / 0.70
min_signals >= 50
candidate publication grid = preregistered
selection rule = calibration only
```

真实发布目标可再加股票/日期簇支持和依赖区间，但第一步先把“同 dev 调 threshold”彻底封死。

### 3.3 unknown / no-entry 不能事后补位

H504 有 `unknown_missing_*` 与 `no_entry`。若一个高分候选在 policy 冻结后已经进入 issued set，事后发现 unknown/no-entry：

- **不得**把它删掉，再用第 k+1、k+2 名补位；
- 否则 outcome 又参与了 candidate selection。

建议每个 dev policy 结果同时保存：

```text
issued_signals
resolved_signals
tp
fp
unknown_signals
no_entry_signals
precision_resolved = TP / resolved issued
precision_issued_lower_bound = TP / all issued
recall_resolved
```

其中 target gate 首轮采用更保守的 `precision_issued_lower_bound`；这样 unknown/no-entry 不会被静默从分母拿掉把 precision 抬高。

## 4. 一个此前没有显式量化的协议下界：H504 三段历史至少需要 1515 个 dense market sessions

当前 `fold_support.py` 已经给出 train→dev 的 dense 理论下界：

```text
minimum_dense_sessions_for_full_maturity_split(H) = 2H + 2
```

H=504 时：

```text
2*504+2 = 1010 sessions
```

但一旦我们要求 **train → calibration → untouched dev** 三段都各有至少一个 full-maturity candidate，dense 理论下界变为：

```text
train signal index = 0
train maturity      = H
calib start         = H+1
calib maturity      = 2H+1
dev start           = 2H+2
dev maturity        = 3H+2
N >= 3H+3
```

所以 H=504：

```text
3*504+3 = 1515 market sessions
```

这还是**每段只有一个 dense candidate 的理论最小值**。现实中还要满足：

- 至少数百 train candidates；
- calibration 最低 signal/support；
- dev 最低 resolved/support；
- 缺失/no-entry/unknown；
- 可能的 embargo；
- 第二复验块。

因此本机真实历史若不足 1515 个已观察 market sessions，不能为了凑 50% 把 calibration/dev 混在一起。正确状态应是：

```text
BLOCKED_PROTOCOL_H504_POLICY
```

然后继续做：

- score 模型开发；
- 因子健康；
- AUX 历史表征；
- forward ledger；

但不能宣称“50% H504 已认证”。
