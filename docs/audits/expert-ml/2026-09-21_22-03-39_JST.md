1. **发现并复核一个会直接改变搜索排名资格的 P1 错误**：`src/ml/search.py` 的 CLI 帮助和注释明确说 `--min-signals` 是“每个 fold 都必须达到”的信号下限，但实际 `eligible` 只检查了**四折总信号数**。因此一个大折可以掩盖小折，当前归档排行榜第 2、3、4 名中已有真实反例。
2. **实现 PIT 候选账本桥接候选**：直接从 `lowzone.build_layers` 的 causal `recall_tier` 生成固定 candidate manifest，不读 `label_* / entry / future_*`，也不在候选阶段做 cooldown，从而给 session-clock H504 标签器一个独立、可指纹化的候选总体。

## 1. 新确认 P1：`--min-signals` 文档说“逐折”，实现却只检查 pooled total

**问题 ID：`EML-P1-SEARCH-MIN-SIGNALS-NOT-PER-FOLD`**

固定源码：
- `src/ml/search.py` 参数定义：<https://github.com/fy-god/pro-web-60d-strategy/blob/4d233e32901168531aaa881d9984b90089b1c8f1/src/ml/search.py#L215-L236>
- ranking 实现：<https://github.com/fy-god/pro-web-60d-strategy/blob/4d233e32901168531aaa881d9984b90089b1c8f1/src/ml/search.py#L338-L381>

参数帮助写的是：

> `out-of-sample signal floor a config must clear across every fold to be RANKED`

但实际资格条件是：

```python
r.get("oos_signals", 0) >= min_signals
and r.get("n_folds", 0) >= min_folds
```

这里的 `oos_signals` 是四折合计，不是逐折下限。`per_fold_signals` 完全没有参与资格判断。

### 1.1 真实归档反例

固定机器结果：<https://github.com/fy-god/pro-web-60d-strategy/blob/4d233e32901168531aaa881d9984b90089b1c8f1/reports/ml_search_wide.json>

默认 `--min-signals=250`。当前归档排序前几名里：

| config | pooled precision | total signals | per-fold signals | 按“每折≥250”应否入榜 |
|---|---:|---:|---|---|
| `wide_rf_32` | 20.8379% | 22,867 | 11,210 / 7,365 / 1,545 / 2,747 | 是 |
| `wide_logistic_37` | 20.4319% | 2,408 | 1,902 / **101** / 321 / **84** | **否** |
| `wide_hgb_14` | 19.4405% | 7,721 | 6,023 / 1,279 / **119** / 300 | **否** |
| `wide_logistic_36` | 19.1251% | 2,766 | 2,213 / **83** / 410 / **60** | **否** |
| `wide_extratrees_26` | 18.9882% | 20,102 | 8,592 / 6,175 / 2,122 / 3,213 | 是 |

所以当前榜单的第 2、3、4 行违反了 CLI 自己声明的逐折支持门槛。它们不是因为 `n_folds<4` 被错误保留，而是因为**每折信号支持很薄，却被 pooled total 掩盖**。

### 1.2 影响

- 这不会推翻 `wide_rf_32` 的 20.84%：它四折都大于 250，仍然合格。
- 它会改变“第二梯队是谁”的排序解释；特别是不能再把 `wide_logistic_37` 或 `wide_hgb_14` 当作通过了“每折至少250信号”的候选。
- 上轮已确认 `ranked_unfiltered` 没有落进 tracked JSON，因此在**不重跑 producer**的前提下不能诚实重建完整的修正后 58 配置排名。不能凭当前截断表宣布新的全局冠军。

### 1.3 候选修复

本轮沙箱候选新增 `search_rank_guard.py` 和一个针对 `src/ml/search.py` 的最小 patch：资格条件改为同时要求：

```python
n_folds >= min_folds
len(per_fold_signals) >= min_folds
min(per_fold_signals) >= min_signals
```

并同步修改 `ranked_basis` 的机器可读说明为“每个 counted fold 均达到阈值”。

回归测试包含上述四个真实归档反例：RF/ExtraTrees 放行，Logistic37/HGB14 拒绝。

## 2. 归档真实 H10：RF 是 pooled 最优，但 ExtraTrees 是更强的“最差折”候选

这不是新 fit；只对 tracked `ml_search_wide.json` 的真实归档折结果做重新统计。

### 2.1 三个可见头部候选

| config | pooled precision | 折 precision SD | 最差折 precision | 最差折 Wilson 95% 下界 | 最大单折信号占比 |
|---|---:|---:|---:|---:|---:|
| `wide_rf_32` | **20.8379%** | 2.257 pp | 18.0583% | **16.2201%** | 49.02% |
| `wide_extratrees_26` | 18.9882% | **0.246 pp** | **18.8016%** | **17.6066%** | **42.74%** |
| `wide_hgb_14` | 19.4405% | 6.022 pp | 18.1969% | 16.0876% | 78.01% |

ExtraTrees 四折 precision 是 `18.94% / 18.80% / 19.23% / 19.33%`，比 RF 的 `22.88% / 18.36% / 18.06% / 20.71%` 平得多。

**结论边界**：
- 若优化目标是 pooled precision，当前归档仍是 RF 更高。
- 若预先定义“最差时间折的二项 Wilson 下界”为稳健性准则，当前这三个候选里 ExtraTrees 更高（17.61% vs RF 16.22%）。
- 这不是“ExtraTrees 已经胜 RF”的最终结论：58 配置本身已经被搜索过，`ranked_unfiltered` 机器产物缺失，而且没有新的 untouched test block。

**下一次 H10 辅助验证应冻结两个候选，而不是继续扫网格**：`wide_rf_32`（精度候选）和 `wide_extratrees_26`（时间稳定性控制）。这只是辅助线，不能替代 H504。

## 3. H504 主线：把自然低位 candidate population 与未来 outcome 解耦

固定源码 `lowzone.build_layers` 明确声明并实现 causal layer stack；只读当前 bar 与历史 bar，`anchor_date/future_*` 等未来列不进入 layer 构造：

<https://github.com/fy-god/pro-web-60d-strategy/blob/4d233e32901168531aaa881d9984b90089b1c8f1/src/lowzone.py#L250-L280>

而当前 `backtest_lowzone.py` 是先把 forward labels merge 到 layer table，再在 resolved rows 上评估版本；这适合旧回测，但不适合作为 H504 研究的 candidate ledger，因为 candidate、outcome、execution 容易再次耦合。

### 3.1 本轮候选实现

本轮沙箱实现 `candidate_manifest.py`：

- 输入仅允许 `code/date/recall_tier`；
- 默认 candidate contract 为 `recall_tier >= 1`；
- 输出 deterministic `candidate_id`、`candidate_known_at`、`candidate_version`、`candidate_reason`；
- 即使输入 frame 同时含 `label_joint / future_max_return / entry_open`，这些字段也不会进入 candidate manifest；
- candidate 阶段**不 dedupe、不 cooldown**。发布/冷却必须是后置 policy，否则会改变自然总体分母；
- 有 prefix-invariance 测试，未来追加行不能改写 cutoff 以前的 candidate ledger（该测试只验证 manifest 层；`lowzone.build_layers` 自身的因果性仍需在本机真实 panel 上做前缀测试）。

这解决的是 H504 研究链中的一个具体接口缺口：

`PIT lowzone layers -> candidate_manifest -> session-clock H504 label oracle -> fold_support -> T0..T5`

不是新的选股因子，也不声称已在真实 panel 上生成 candidate 数量。

## 6. 下一次本地 agent 的有依赖队列

### WP1 runtime + receipt
读取实际 `fixup_prompt`、runner timeout、Windows 已注册任务的 `ExecutionTimeLimit`，生成 `local_start_receipt.json`。若仍短于三小时，只修本任务运行时上限；不改触发时刻/频率，不重建其他任务。

### WP2 candidate ledger
在真实 panel 上运行 causal `lowzone.build_layers`，生成 `recall_tier>=1` 的 PIT candidate manifest；保存候选数、股票数、日期范围、candidate hash 和 32 股票前缀不变测试。不得先 join future outcome 再决定 candidate。

### WP3 H504 outcome + fold support
用 session-clock H504 oracle 生成 `entry_session/deadline/label_end/known_at/training_eligible_at` 和 risk-first outcome ledger。再运行 fold_support；没有成熟 train->成熟 dev 时明确 `BLOCKED_PROTOCOL_H504`。

### WP4 合法 H504 训练或 AUX_REAL_HISTORY
若有合法 H504 开发折，优先跑预登记 T0 与 T3 配对，再扩 T1/T2/T4/T5；若没有，运行真实历史 AUX base-vs-plus 表征分支。AUX 结果不得写成 H504 precision。

### WP5 表格/神经和完整预测
满足 G1 后继续 HGB、MLP、TCN；每次 fit 保存模型、reload 一致性、全开发 candidate predictions、train history、seed/fold 和 hash。smoke 不算正式 fit。

### WP6 错误驱动再训
从完整预测做 FP/FN/risk/timeout/no-entry/unknown 分层，选择一个有样本支持的机制做一次 paired change；负结果保留。

### WP7 H10 辅助冻结验证
若存在真正未曝光 H10 时间块，仅冻结 `wide_rf_32` 与 `wide_extratrees_26` 两臂，不再重新搜索 58-config 网格。修正 per-fold min-signals guard 后再报告资格。

### WP8 交接
输出 `experiment_registry.jsonl`、checkpoint hash、完整 predictions、candidate/outcome/feature/split hash、`execution_receipt.json` 和精确 resume 命令。没有这些，不把本机三小时标为完成。
