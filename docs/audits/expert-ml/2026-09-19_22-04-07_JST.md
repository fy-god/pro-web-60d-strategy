# 2. 证据化错误清单

## EML-P0-AUDIT-STALE-ATTEST — PASS 与最终发布树不绑定【P0，新增确认】

**固定源码：** `82aefeb583ac6f039cc67ae2582c30803fc7cb32`

**文件 / 函数：** `scripts/scheduled_report_audit.py::changed_reports()`、`main()`、`commit_and_push()`。

最小调用链：

```python
# 1) 只 fetch + diff，不更新当前 HEAD
changed = git_diff(HEAD, origin/main)

# 2) checker 仍检查当前本地工作树
code = run(audit_reports.py)

# 3) 先写 PASS status 并 commit
commit(AUDIT_STATUS.md)

# 4) push 失败后才 rebase 到最新 origin/main
rebase(origin/main)

# 5) 不重跑 checker，直接再次 push
push(HEAD:main)
```

**当前真实触发证据：** 已发布 `AUDIT_STATUS.md` 是 `PASS`，同时列出两个 `Remote drift` 路径。这说明当前生产路径实际进入过“checker 运行时本地树 != origin/main”的分支。

**独立反例：** 本轮临时 Git 仓库中，把远端 `reports/result.json` 从 `valid=true` 改成 `valid=false`。本地旧 checkout 经过当前控制流后，最终远端得到 `valid=false` + `Verdict: PASS`。

**错误机制：** attestation 的被测对象没有冻结；`PASS` 没有绑定 `audited_head_sha`，而 rebase 会改变最终提交祖先树。

**影响方向：** 可能产生假 PASS。任何 concurrent remote commit 只要改变 checker 应看的输入，都可能让状态认证错误的树。当前 drift 恰好是审计文档，不代表本轮已有市场数字被误认证，但控制流已经被真实触发。

**修改方法：** 二选一，推荐 A。

A. detached/frozen audit：

```text
git fetch origin main
AUDITED_SHA = origin/main
git worktree add --detach <tmp> AUDITED_SHA
在该 worktree 运行 audit_reports.py
记录 AUDITED_SHA + artifacts hash
若发布 status 前 origin/main != AUDITED_SHA：废弃本次结果，重新审计
仅对完全相同 AUDITED_SHA 写 PASS
```

B. 原地同步：先 `fetch -> rebase/reset` 到 `origin/main`，确认 clean worktree，再运行 checker；之后如果远端 HEAD 变化则重新跑，禁止把旧 PASS rebase 到新树。

**回归输入：** 两个本地 clone + bare remote；在 checker 前让 writer 提交一个会让 checker 失败的新 report。

**预期：** 最终远端不得出现“新失败 report + 旧 PASS”；应得到 `STALE/RETRY` 或在同步后重新执行并正确 FAIL。

## EML-P1-AUDIT-DRIFT-PASS — 有 remote drift 时 headline 仍写 PASS【P1，新增确认】

**文件 / 函数：** `scripts/scheduled_report_audit.py::write_status()`。

当前：

```python
ok = code == 0 and not unstable
```

`changed` 不参与 `ok`，所以 current status 同时显示 `PASS` 和 `2 path(s) differ from origin/main`。

后面的 `needs_attention = code != 0 or bool(changed) or bool(unstable)` 又把 drift 当 attention，形成同一份运行内部两套 verdict 语义。

**影响：** 人或自动化只看 status 顶部 PASS 会忽略“本次 checker 并未验证最新远端树”。

**修法：** 如果采用上面的 frozen-SHA 方案，状态应明确区分：

```text
PASS      = audited_sha == published_sha 且 checker=0
FAIL      = checker != 0
STALE     = remote head changed after audit
UNSTABLE  = 本地被审计 artifact 审计中途变化
```

不得用一个 PASS 再附一段 remote drift 来表达 stale。

**回归：** `changed != []` 时，顶层 verdict 绝不能是 PASS。

## EML-P1-AUDIT-PUSH-SCOPE — `HEAD:main` 仍可夹带本地已有 commit【P1，静态风险，未确认发生】

**文件 / 函数：** `commit_and_push()`。

函数注释假设“只 ever commit `AUDIT_STATUS.md`”，但代码在第一次尝试直接：

```text
git push origin HEAD:main
```

如果进入函数前当前分支已经领先 `origin/main` 一个无关本地 commit，它也会一并被推送。当前这一轮 `Remote drift` 更符合“本地落后远端”的场景，不能拿它证明此风险已经发生；所以本项保持静态风险，不升级成确认事故。

**修法：** status publisher 应从 frozen remote SHA 新建单提交临时分支/worktree；发布前断言：

```text
HEAD^ == audited_remote_sha
changed_paths(HEAD^..HEAD) == {reports/AUDIT_STATUS.md}
```

否则拒绝 push。

# 4. 本轮主改造：Attested Causal Research Pipeline

本轮主改造不是“再加一道日志”，而是把 **研究版本认证** 和 **H504因果模型链** 连成一个不可漂移的协议。

## 4.1 目标

任何 headline 必须能回答：

```text
这条数字来自哪个 source SHA？
哪个 TaskSpec？
哪个 data / calendar / candidate / matrix hash？
哪些 base-model OOF predictions？
哪个 calibration 和 publication policy？
最终 GitHub PASS 实际检查的是哪个 commit？
```

## 4.2 非目标

- 不把 H10/+30%/High 改名冒充 H504；
- 不把阈值提高当模型信息增量；
- 不通过删除 unknown / entry-unavailable 来提高 precision；
- 不让 report publisher / fixup agent / checker 互相通过自然语言暗示“已经验证”。

## 4.3 冻结对象与 schema

统一生成 `release_manifest.json`（未来实现，不在本轮写入）：

```json
{
  "source_sha": "...",
  "task_hash": "...",
  "calendar_hash": "...",
  "universe_hash": "...",
  "candidate_hash": "...",
  "feature_hash": "...",
  "labels_hash": "...",
  "oof_prediction_hash": "...",
  "calibration_hash": "...",
  "policy_hash": "...",
  "ledger_hash": "...",
  "audited_commit": "..."
}
```

Candidate / Outcome / Publication / Execution 分表；publication 先冻结再关联 future outcome。

H504 TaskSpec 继续固定：

```yaml
task_id: joint_close4x_H504_low80_v1
decision: t_close
entry: next_market_session_open
goal: close > 4E
risk: low < 0.8E
horizon_market_sessions: 504
same_session_priority: risk
```

## 4.4 自动化认证原则

报告 checker 必须在 detached `AUDITED_SHA` 上运行；status 只认证该 SHA。fixup agent 只生成 working-tree diff + `fix_manifest.json`；最终 path allowlist、tests、audit、commit、push 由 deterministic launcher 执行。这样 agent 不能自己既当修复者又当发布权限控制器。

**完成标准：** 同一 candidate 在任何下游入口都携带同一 `task_hash/calendar_hash/universe_hash`。

## WP3 — 标签与 known-at 单一真源

**文件：** `src/labels.py`、`src/backtest_lowzone.py`、`src/ml/final_holdout.py`、所有 search/calibration/meta 入口。

新增 `label_end/known_at/entry_session/deadline/status`；H504按 market session、Close goal、risk-first。所有 fit/threshold/calibration/meta 入口共享 `asof_guard()`。

**回归：** 停牌、跨年、尾部删失、同日goal+risk、exact 4E、0.8E边界。

## WP4 — 修低位机制与 expert family

**文件：** `src/lowzone.py`、`experts/strategies/pullback_retest.py`、`gap_follow_through.py`、strict wrappers。

用窗口成交量总和/覆盖率重建 pressure；raw physical value、quality、gate分开；shallow pullback和gentle gap采用有界质量函数；strict threshold clones标同一 `family_id`。

## WP5 — 固定候选总体 + 真正 OOF + competing-risk H504

base learners只能输出时间外分数；第二层只读OOF。H504采用离散 competing risk buckets，例如 1–21、22–63、64–126、127–252、253–378、379–504。

输出 goal hazard、risk hazard、survival 与累计 joint probability；unknown不伪负。

## WP6 — 独立校准 + 因果 publication ledger

校准集与调参分开；训练加权score不叫真实概率。publication 先于 outcome；cooldown读取独立 `market_session_id`；unknown / execution unavailable 不删除、不补位。

## WP7 — 统计、event Recall、frontier与依赖

候选自然基率与signal precision分开聚合；0-signal fold仍进候选分母。scalar frontier只在tie group边界；Top-K单列。报告整数TP/FP、未知、不可执行、股票数、日期簇、event Recall、Brier/log-loss、cluster-aware interval。

## WP8 — release manifest + clean-SHA attestation

README/JSON/CSV/AUDIT_STATUS headline必须引用同一 manifest；checker不仅做内容算术，还校验 manifest、source SHA、matrix/prediction/policy hash。PASS绑定一个不可变 commit，不绑定“当前工作树”。
