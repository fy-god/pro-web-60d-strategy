## 2. 新 P1：dev 候选够多不等于 dev 可评分样本够多

**`EML-P1-H504-DEV-SUPPORT-COUNTS-CANDIDATES-NOT-RESOLVED-001`**

### 2.1 当前结构性问题

`fold_support.enumerate_mature_splits()` 只看：

- candidate date 是否在日历上；
- candidate date 是否有完整 H504 日历成熟度；
- train candidate 数；
- dev candidate 数。

它不知道 outcome ledger 里哪些候选最终是：

- `success`
- `risk`
- `timeout`
- `no_entry`
- `unknown_missing_price`
- `unknown_missing_bar`

因此这个 structural fold support 只能回答“日历/候选几何上可能存在 train→dev”，不能回答“dev 有足够 resolved supervision”。

### 2.2 `run_h504_hgb()` 已经算了 resolved，但没有用它做 gate

当前代码顺序是：

```python
split = first_legal_split(cal, data['date'], ...)
dev = data['date'].between(dev_start, dev_end)
resolved = dev & data.label_joint.notna()

if train.sum() < min_train_candidates or dev.sum() < 50:
    return BLOCKED_PROTOCOL_H504
```

关键问题是最后检查的是：

```text
dev.sum()
```

而不是：

```text
resolved.sum()
```

随后：

```python
ydv = data.loc[resolved, 'label_joint']
```

所以可以出现：

```text
n_dev_candidates >= 50
n_dev_resolved << 50
甚至 n_dev_resolved = 0
```

但仍然通过当前 dev-support gate。

### 2.3 当前 metrics 路径还会容忍 0 resolved

当前 metric 代码显式允许空 `ydv`：

- `logloss = None if len(ydv)==0`
- `brier = None if len(ydv)==0`
- `average_precision = None if no positive`
- `base_rate = None if len(ydv)==0`

最后仍然构造：

```text
status = COMPLETE_H504_DEV
```

只要训练集本身有两类、模型 fit 成功、dev feature prediction 能生成，就没有第二个 resolved-support fail-closed。

这意味着“有 dev_predictions.csv”或“registry 中 COMPLETE_H504_DEV”**目前不足以证明这个 dev block 有可认证的 H504 开发集成绩**。

## 3. 为什么这条 P1 直接影响 50% / 70% 目标

H504 的 publication precision 至少需要区分两个分母：

1. **resolved precision**：在已经有合法结果的已发行信号中，TP / resolved issued；
2. **issued lower-bound precision**：TP / all issued，把当前 unknown/no-entry 保留在发行账本里，不允许事后删除或补位。

如果 dev block 本身 resolved 数太小，那么：

- AP / Brier / logloss 没统计稳定性；
- 一个或几个 success 就可能制造极高 precision；
- 50% / 70% 结论没有足够支持；
- no-entry / unknown 不能通过“只看有标签行”从发行分母中消失。

因此正式协议必须把：

```text
candidate support
resolved support
positive support
negative support
issued accounting
```

分别写清楚。

## 5. 建议的窄产品修复

不要重构整个研究栈，只在现有 H504 路径增加 outcome-aware gate。

### 5.1 fold support 分两层

保留现有：

```text

```

再在 outcome ledger 生成后新增：

```text

```

每个预注册 dev block 至少记录：

```text

```

### 5.2 模型 fit 前 fail-closed

首版建议：

```text
n_dev_candidates >= 50
n_dev_resolved >= 50
n_dev_positive >= 1
n_dev_negative >= 1
```

若不满足，返回：

```text
BLOCKED_PROTOCOL_H504_RESOLVED_DEV
```

不要写 `COMPLETE_H504_DEV`。

50 只是当前与既有 dev candidate 最低门保持一致的首版安全值，不代表统计充分性已经证明；后续 frozen publication policy 还要有自己的 calibration/dev 最小信号数要求。

### 5.3 registry 与 metrics 必须持久化 support

每次真实 fit 至少写：

```text

n_dev_resolved
n_dev_unknown
n_dev_positive
n_dev_negative
resolved_fraction
fold_id
outcome_ledger_hash
```

这样以后不能只看 `status=COMPLETE` 判断成绩有效。
