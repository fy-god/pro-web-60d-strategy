**机制（三臂复现，单变量隔离）**

被测的是"远端新增了路径 P、本地恰好有一个 **untracked** 文件也在 P"：

| 臂 | 设置 | 预期 | 实测 |
|---|---|---|---|
| POSITIVE | 远端 **新增** P；本地有 **untracked** P | rebase 失败 | `rc=1`，原文 `error: The following untracked working tree files would be overwritten by checkout` + `Aborting` |
| NEGATIVE | 同上，唯一差别是本地 untracked 文件在**另一个**路径 | rebase 成功 | `rc=0`，`Rebasing (1/1)` → `Successfully rebased` |
| CONTROL | **同一** P，但本地该文件是 **TRACKED（staged）**、内容与远端**完全相同** | rebase 成功 | `rc=0`，`Created autostash` → `Rebasing (1/1)` → `Successfully rebased` |

- 三臂的核心差异只有一个变量：**untracked 与否 / 路径是否碰撞**。POSITIVE 与 NEGATIVE 的差别仅仅是**路径**，结果相反 → 探针有判别力。
- CONTROL 排除了"内容冲突"这个混淆变量（内容改成完全相同仍成功），把原因锁定在 **untracked-ness**。
- 根因：`git rebase --autostash` 只 stash **tracked** 的修改，**不 stash untracked 文件**；checkout 目标提交时遇到会被覆盖的 untracked 文件即拒绝。

**影响**
- 远端 `reports/AUDIT_STATUS.md` **冻结在 `a8ae13c`（2026-09-22 03:15）**；远端最后一次触及该文件的提交确为 `a8ae13c`。
- 本地 `main` 相对 `origin/main`：**ahead 8 / behind 35**，merge-base 恰为 `a8ae13c`——即**分叉点就是最后一次成功发布的那次提交**，时间线完全吻合。

- 该发布器自述的历史故障（`:213-215`）是"plain `git push` 输掉竞态、提交悬空"；本轮证明**修法本身引入了一个新的、不会自愈的死锁**：只要那两个 untracked 残留还在，rebase 每次都在同一处 abort，重试 3 次也没有意义（`:257-260` 是**直接 return**，不进 `continue`）。
- 影响面：`reports/AUDIT_STATUS.md` 是全仓库 629 项一致性检查的对外落点；它停更即**该仓库的对外质量状态隐身 28 小时**。

**修复建议**
1. `:255-256` 的 rebase 前先处理 untracked 冲突。最小改动：把 `--autostash` 换成显式两步，或先 `git stash push --include-untracked`（把 untracked 也收进去）、rebase 后再 `pop`。
