## 1. 实时源码证据

### 1.1 `train_h504.py` 只取第一条合法 split

当前 `src/ml/research_h504/train_h504.py`：

```python
def first_legal_split(...):
    s = enumerate_mature_splits(...)
    if s.empty:
        return None
    return s.iloc[0].to_dict()
```

`run_h504_hgb()` 随后只执行：

```python
split = first_legal_split(...)
dev_start = split['dev_start']
dev_end = split['dev_end']
...
fit one HGB
write one dev_predictions.csv
return COMPLETE_H504_DEV
```

当前接口没有 `fold_id`、`dev_block_index`、`all_folds`、`nonoverlap` 或第二开发块参数。

因此只要 H504 开始能形成合法时间折，当前程序会固定在**最早出现的那一个合法 dev block**上评价，而不会自动验证后续市场阶段。

这直接违反 v5 的 WP7 目标：第二合法开发块必须是独立复验，而不是复用第一块的大部分日期。

### 1.2 `fold_support.py` 枚举的是每日滑动 dev 窗，不是独立 folds

当前 `enumerate_mature_splits()` 的循环为：

```python
for dev_start_i in range(1, len(cal)):
    dev_end_i = min(len(cal) - 1, dev_start_i + dev_block_sessions - 1)
```

也就是说，`dev_start_i` 每次只增加 1 个 market session。

默认：

```text
dev_block_sessions = 63
```

那么：

```text
split[0] = sessions [s, s+62]
split[1] = sessions [s+1, s+63]
```

两者重叠：

```text
62 / 63 = 98.412698...%
```

所以以后绝对不能把：

```python
splits.iloc[0]
splits.iloc[1]
```

称为“两个开发折”。它们几乎是同一块数据。

## 2. 为什么这会直接污染“50% 有没有稳定达到”的判断

上一轮已经确认 H504 需要 train → calibration → untouched dev 才能冻结 publication policy。本轮再加一层：**一个 untouched dev 仍不足以证明 50% 在时间上稳定。**

如果模型只在最早合法 dev 得到一次 50%，而下一市场阶段完全失败，当前代码不会自动暴露这个问题。

反过来，如果把滑窗 `splits.iloc[1]` 当作第二折，第一折和第二折共享 98.41% 的日期，得到两个相近 precision 也几乎没有新增独立证据。

因此真正的 H504 时间外证据应该至少区分：

```text
score-model fit block
calibration block
untouched dev block A
untouched dev block B（如果历史支持）
```

其中 A/B 必须是**不重叠 market-session block**；若需要 embargo，则 B 的开始还要严格晚于 A.end + embargo。

零信号块也必须进入总体结果，不能因为某个 regime 没有 issued signals 就把该块从稳定性统计中删掉。

## 4. 正确接入方案

### 4.1 `fold_support.py`

保留当前逐 session 的 `enumerate_mature_splits()` 作为**支持扫描器**，但增加显式 fold-plan 层，例如：

```text
select_nonoverlapping_mature_dev_blocks(...)
```

至少要求：

```text
next.dev_start_i > previous.dev_end_i + embargo_sessions
```

并在打开模型预测前冻结：

```text
fold_plan_version
calendar_hash
candidate_hash
fold_id
dev_start
dev_end
n_train
n_dev
n_dev_resolved
```

不能训练完后再挑表现好的块。

### 4.2 `train_h504.py`

`first_legal_split()` 不应继续作为正式研究唯一入口。

正式入口应接收明确 `FoldSpec`，至少支持：

```text
T0..T5 × DEV_A
T0..T5 × DEV_B（若存在）
```

每个 dev block 单独保存：

```text
model/checkpoint
calibration_predictions
frozen_policy.json
dev_predictions.csv
policy_metrics.json
```

然后额外生成 `fold_metrics.csv`，不能只给 pooled precision。

### 4.3 稳定性验收

每个不重叠 block 至少记录：

```text
candidate_count
issued_signals
resolved_signals
tp
fp
unknown
no_entry
precision_issued_lower_bound
precision_resolved
recall_resolved
base_rate
lift
AP
Brier
log-loss
```

目标 50%/70% 必须报告：

```text
per-block target status
pooled target status
minimum-block precision
zero-signal blocks
```

不能用一个高 precision block 覆盖另一个零信号或低 precision block。

## 6. 与上一轮 publication-policy 结论的关系

上一轮的 train → calibration → untouched dev 结论仍然成立；本轮补充的是**跨时间复验层**。

建议正式协议按以下顺序落地：

```text
G1 data/label gates
→ candidate/outcome ledger
→ frozen non-overlapping fold plan
→ train
→ calibration-only publication policy
→ untouched DEV_A
→ untouched DEV_B（历史支持时）
→ per-fold + pooled metrics
```

这两个门必须同时成立，才能避免：

- 同 dev 调 threshold；
- 只挑最早/最好一个 dev；
- 把98%重叠滑窗伪装成复验。
