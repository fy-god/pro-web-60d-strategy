## 0. 本轮新增结论

新增 P1：`EML-P1-H504-STOCK-CODE-KEY-NORMALIZATION-MISMATCH`。

当前 H504 candidate ledger、panel/labeler 对 `code` 使用了**两套不同的规范化规则**：

- `candidate_manifest.py`：`src["code"] = src["code"].astype(str).str.zfill(6)`；
- `data_io.prepare_panel()`：只有 `p['code'] = p['code'].astype(str)`；
- `task_spec.label_h504_candidates()`：panel 与 candidates 也都只做 `astype(str)`，然后用字符串 `code` 作为 `arrays` 字典键。

因此，只要上游 `code` 是合法但未补零的 `1` / `"1"` / 数值型 `1.0`，candidate manifest 会变成 `"000001"`，panel 仍是 `"1"`；labeler 查 `arrays.get("000001")` 失败，随后把**本来存在且有合法 t+1 Open 的候选静默记为 `no_entry`**。

这不是美观/展示问题：`no_entry` 会直接改变 H504 outcome ledger、resolved 数量、fold 支持、自然总体分母与后续训练样本，因此按研究证据完整性定为 **P1**。

## 1. 源码证据链

### 1.1 candidate 端强制补 6 位

`src/ml/research_h504/candidate_manifest.py`：

```python
src["code"] = src["code"].astype(str).str.zfill(6)
```

candidate_id 也基于这个补零后的 code 生成。因此 candidate ledger 一旦生成，键已经固定为 `000001` 形式。

### 1.2 panel / label 端不做相同规范化

`src/ml/research_h504/data_io.py`：

```python
p['code'] = p['code'].astype(str)
```

`read_table()` 对 CSV 只是 `dtype={'code':'string'}`，只保证它是字符串，**不会把 `"1"` 变成 `"000001"`**；Parquet 则直接 `pd.read_parquet()`，数值型代码也允许进入。

`src/ml/research_h504/task_spec.py` 同样只做：

```python
p['code'] = p['code'].astype(str)
c['code'] = c['code'].astype(str)
```

之后 panel 被建成：

```python
arrays[code] = (...)
```

candidate 则通过：

```python
stock = arrays.get(code)
entry = stock[0][i+1,0] if stock is not None else np.nan
if not np.isfinite(entry) or entry <= 0:
    r.update(outcome_class='no_entry', ...)
```

所以 code 格式一旦不一致，不会 fail closed，也不会报「unknown code」；它会伪装成交易日存在但无法入场的业务结果 `no_entry`。

### 1.3 当前测试恰好掩盖了这个问题

`tests/research_h504/test_candidate.py` 的公共 `_panel()` 默认：

```python
def _panel(n=510, code="000001", base=10.0):
```

也就是说现有大多数 H504 contract tests 从一开始就喂入已经补齐的 `000001`。15:40 审计跑出的 `65 passed` 因而**不能覆盖 unpadded/numeric code 这条输入路径**。本轮不重复冒充那 65 项为本轮执行成绩。

## 2. 本轮实际反例：有效 t+1 Open 被改成 `no_entry`

我在隔离沙箱用当前 `candidate_manifest` + `task_spec` 的真实语义构造最小面板：

```text
calendar      = 2024-01-02, 2024-01-03, 2024-01-04

candidate源   = int 1, recall_tier=1
```


这里的关键点不是 H=2，而是**entry 查找发生在 horizon 之前**；正式 H=504 会发生相同 code-key 失配。


也就是说修复前后唯一改变的是 key canonicalization；本来存在的入场不再被误判为 no-entry。

## 3. 影响范围与严重度

### 3.1 CSV 也会触发，不只 Parquet

当前 CSV loader 强制 `code` 为 pandas string，但 `"1"` 仍然是 `"1"`。所以以下两类都可能触发：

1. CSV：`code` 列写成 `1` 而不是 `000001`；
2. Parquet：`code` 是整数或整数型浮点列。

因此这不是「某个 pandas 推断偶发」；它是当前公开输入接口允许的合法表示差异。

### 3.2 可造成批量伪 `no_entry`

如果一批真实 panel 的股票代码整体是 unpadded/numeric，而 low-zone layers 来自同一批数据：

1. layers 进入 candidate manifest 后全部被 zfill；
2. panel 保留 unpadded string；
3. H504 labeler 对大量候选 `arrays.get(code)` 失败；
4. 这些候选被写为 `no_entry`，不是 error；
5. candidate-aware fold、resolved support、base rate 与真实 fit 都在错误 ledger 上继续工作。

因此必须在任何真实 `candidate_manifest → label → fold → fit` 之前修掉。

### 3.3 还有一个键别名副作用

panel 当前在只 `astype(str)` 后做 duplicate 检查。若同一数据源同时出现 `1` 与 `000001`、同一日期，它们会被视为两个不同股票键，不会在 panel duplicate guard 中冲突；candidate manifest 反而会把二者都 zfill 成同一个键并在 candidate_id 阶段失败。

正确顺序应是：**canonicalize → 再做 key-null/duplicate 检查**，这样别名不会在不同模块获得不同含义。

## 4. 最小修复设计（只下发候选，不远端改产品源码）

建议增加一个共享 stock-code canonicalizer，而不是在第三个位置继续手写 `zfill`。

### 4.1 规范化合同

- plain integral A-share code `1` / `1.0` / `"1"` → `"000001"`；
- 已是 `"000001"` / `"600000"` 保持；
- **不要**对任意 exchange-qualified / alphanumeric identifier 盲目 `zfill`，例如 `1.SZ`、`SH600000` 应先按明确 schema 处理，而不是变成怪异字符串；
- null / empty key fail closed；
- canonicalization 必须发生在 duplicate check 之前。

### 4.2 需要接入的位置

1. `data_io.read_table/prepare_panel`：panel key；
2. `candidate_manifest.build_candidate_manifest`：candidate key，替换局部 `str.zfill(6)`；
3. `task_spec.label_h504_candidates`：panel 与 external candidate 两侧都复用同一 helper；
4. 显式 `feature_source` 在任何 candidate join 之前也必须使用相同 helper；
5. receipt/data inventory 增加 code schema 摘要：dtype、plain-digit 比例、canonicalization version、alias collision count。

### 4.3 验收测试

至少补以下回归：

- CSV `code="1"` → candidate/panel 都为 `000001`，有效 t+1 open 不得变 no-entry；
- Parquet/numeric `code=1` 与 `code=1.0`；
- already padded `000001`；
- 非 plain identifier 不被盲目补零；
- `1` + `000001` 同日 alias collision 在 canonicalize 后 fail closed；
- candidate_id/panel key/feature-source key 三者完全一致；
- future perturbation 不改变 prefix candidate key；
- 正式 H504 label 结果只因行情/合同变化，不因文件格式改变。

完成标准：同一逻辑证券使用 CSV-string、Parquet-int、Parquet-float 三种编码，`candidate_id / entry_session / entry_open / outcome_class / label_joint` 必须一致。

回滚：移除共享 canonicalizer 并恢复三个调用点；不需要迁移历史原始行情，但**旧 experiment registry/candidate manifest 若由不一致 code schema 产生，不可继续复用，应按 input/schema hash 失效**。

## 9. 本轮结论

本轮没有市场成绩，但发现了一个必须在真实训练前修的**实体主键 P1**：candidate 端补零、panel 端不补零，使一个有明确 t+1 `Open=11.0` 的合法候选被当前 labeler 静默写成 `no_entry`。候选 guard 已用同一 counterexample 将 `entry_open` 恢复为 11.0，并通过 4 个额外软件测试。

因此下一轮最有价值的进展不是再新增模型/因子，而是本地 agent 把统一 key contract 落地、真实 panel 做 alias/coverage 统计，然后才继续 H504 ledger/fold/fit。
