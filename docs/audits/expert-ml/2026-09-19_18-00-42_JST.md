# 2. 增量结论

## 2.1 本轮没有新的市场模型改进提交

当前模型、标签、低位特征、walk-forward、holdout、横截面模块与上一审计源码完全同 blob。现有 H10 数字仍是旧归档，不能称本轮训练结果：

- RF 开发 walk-forward：`4765 / 22867 = 20.8379%`；
- HGB 开发 walk-forward：`1996 / 12143 = 16.4375%`；
- HGB 2026 历史 holdout：`844 / 6202 = 13.6085%`，base `2.8958%`；
- holdout 归档 1194 只股票、150 个信号日期，日期聚类区间约 `[10.24%, 17.59%]`。

这些均是 **H10 / +30% / High** 任务。当前用户主任务 H504 / Close>4E / Low>=0.8E 仍没有可认证的同口径结果。

## 2.2 最大新增问题不是分类器，而是“审计 → 自动改码 → 直接 main”的发布控制

`318fb47...` 把审计报告变成了另一个 full-access agent 的输入，并允许它直接 commit/push `main`。这个方向可以减少人工搬运，但现在的 launcher 在同步失败时是 **fail-open**，并且“允许改哪些文件、是否已经验证、是否允许 push”主要依赖自然语言 prompt，而不是机器门禁。

在这种架构下，任何模型修复之前，应先把“修复执行器”从**自由写入 agent**改成“agent 只产本地 diff + launcher 做确定性验收和 push”。否则后续审计即使判断正确，也存在被执行层错误实现或在脏基线上应用的风险。

# 3. 证据化错误清单

## EML-P0-FIXUP-SYNC-FAILOPEN【新确认，未修】

**固定源码：** `scripts/run_fixup.py @ 318fb47...`

当前最小代码：

```python
run_git(["fetch", "origin", "main"], log)
sync_code = run_git(["rebase", "--autostash", "origin/main"], log)
log.write(f"rebase exit: {sync_code}\n\n")
...
completed = subprocess.run([str(dsh), "--profile", "headless", TASK], ...)
```

`fetch` 返回码完全未检查；`rebase` 返回码只写日志、不控制流程。只要 prompt 和 dsh 存在，即使 fetch 或 rebase 失败，仍然启动具有 `danger-full-access` 的修复 agent。

### 反例

R6 对上述控制流做等价最小执行：

```text
fetch=1, rebase=1 -> agent_started
fetch=1, rebase=0 -> agent_started
fetch=0, rebase=1 -> agent_started
```

### 错误机制

- fetch 失败：`origin/main` 可能是旧 ref，agent 看不到最新报告／修复；
- rebase 失败：工作树可能存在冲突或 rebase state，agent仍开始改代码；
- 后续 agent 再 fetch/rebase/push 时，已经是在错误基线上完成了复现和修改；
- 这不是普通“日志不漂亮”，而是自动写 main 的前置一致性条件没有 gate。

### 影响方向

无法事先界定是乐观还是悲观：可能漏修、重复修、在旧源码上做错误补丁，或把未解决冲突与新的 agent 修改混合。

### 修改方法

launcher 自己负责确定性同步门禁：

```python
fetch_rc = run_git(...)
if fetch_rc != 0:
    return FAIL_SYNC

rebase_rc = run_git(...)
if rebase_rc != 0:
    run_git(["rebase", "--abort"], ...)
    return FAIL_SYNC

assert_no_rebase_state()
assert_clean_worktree_except_explicit_local_logs()
assert head_is_ancestor_of_origin_main_or_equal()
```

agent 启动前保存：

```text
base_head
origin_main
git_status_porcelain
latest_report_path
latest_report_blob
```

### 回归输入与预期

1. fake `git fetch` exit 1：不得启动 agent；
2. fake `rebase` exit 1：执行 abort，agent 启动计数必须为 0；
3. dirty tracked source：拒绝开始；
4. success path：才允许 agent。

## EML-P1-DOWNVOL-EMPTY【未修，重新确认】

**固定源码：** `src/lowzone.py::build_layers`

```python
down = np.where(close < prior, volume, np.nan)
up = np.where(close >= prior, volume, np.nan)
down5 = rolling(5, min_periods=3).mean()
up5 = rolling(5, min_periods=3).mean()
down_vol_ratio5 = down5 / up5
```

同一天只能属于 down 或 up。5 日窗口要求两侧各 >=3 个有效样本，需要至少 6 天，逻辑上不可能。

R1 穷举 32 种五日涨跌组合：`0 / 32` 能产生有限比值。

### 修改

不要补 0 掩盖。新增版本化量压特征，例如：

\[
D_w=\sum_{d\in down} volume_d,\quad
U_w=\sum_{d\in up} volume_d,
\]

\[
pressure_w=\frac{D_w-U_w}{D_w+U_w+\epsilon}
\]

同时保存 `n_down`、`n_up`、coverage 与 one-sided flag。它是“下跌日 vs 上涨日成交量偏向”，不是资金净流。

# 4. 新增执行链风险：与确认错误分开

## EML-P0R-FIXUP-UNSCOPED-MAIN【高风险设计，尚未观察到真实误推】

`run_fixup.py` 强制：

```python
env["DSH_PERMISSION_MODE"] = "danger-full-access"
```

`fixup_prompt.txt` 允许 agent 直接：

```text
git commit
git fetch
git rebase
git push origin HEAD:main
```

生产 launcher 没有确定性文件 allowlist，也没有在 push 前由 launcher 校验：
- 实际改了哪些文件；
- 是否只改报告所允许的 issue/file；
- 是否修改了 `.github/`、审计 prompt、调度器、数据或报告；
- 是否测试命令真实执行；
- 是否 commit 的 parent 是它开始复现时的已核验 base。

仓库的 E2E probe 证明了 toy agent **能 push**，并在 toy prompt 下只改了两个文件；它没有证明生产 prompt 在任意报告内容下都只能改白名单路径。

### 建议

**agent 不再拥有 push 责任。**

```text
launcher sync+freeze base
        ↓
agent 只产生本地 diff + fix_manifest.json
        ↓
launcher deterministic validate:
  path allowlist
  base_sha
  issue ids
  tests command + exit code
  no audit-dir/.github/scheduler mutation
        ↓
launcher commit/push
```

高风险路径默认 deny：
`docs/audits/**`、`.github/**`、`scripts/run_fixup*`、`scripts/fixup_prompt.txt`、scheduler 注册文件、密钥／环境配置、数据文件。若某个审计问题确实要求改这些控制面文件，必须人工单独授权，不让审计正文自动提升权限。

## EML-P1R-FIXUP-STATE-NONTRANSACTIONAL【静态风险】

`last_processed.txt` 由 agent 按 prompt 自己写，本机日志状态与远端 commit 没有事务绑定；文件丢失时退化为“看最近 15 条 git log 猜是否处理过”。

### 建议

launcher 在**远端回读 push commit 成功之后**才写 marker；远端 commit message 添加结构化 trailer：

```text

Audit-Blob: <sha>
Fix-Manifest: <sha256>
```

是否已处理优先从 Git 历史的 trailer 判断，本地 marker 只是缓存。

自由文本 Markdown 同时承担“证据”和“自动执行指令源”。报告会引用代码、错误消息、第三方文本；full-access agent 不应把任何自然语言片段都视为控制面。

## 6.3 H504 改为离散时间 competing-risk，而不是单个 504 日二分类

定义事件：

- G：首次 `Close > 4E`；
- R：首次 `Low < 0.8E`；
- 同一 market session 同时发生时标 R；
- 504 日都未发生为 horizon timeout；
- 数据行政截尾为 censored，不伪负。

使用起始时间桶：

```text
1-21
22-63
64-126
127-252
253-378
379-504
```

对仍处于风险集的候选，在桶 k 预测条件 hazard：

\[
h_{G,k}=P(G\text{ in }k\mid alive_k,x),
\]

\[
h_{R,k}=P(R\text{ in }k\mid alive_k,x),
\]

\[
h_{0,k}=1-h_{G,k}-h_{R,k}.
\]

生存概率：

\[
S_{k}=\prod_{j\le k} h_{0,j}.
\]

最终联合目标概率：

\[
P_{\text{joint}}
=\sum_k S_{k-1}h_{G,k}.
\]

风险先发生概率：

\[
P_{\text{risk}}
=\sum_k S_{k-1}h_{R,k}.
\]

这比 `1 - label_joint` 更有解释性：timeout、risk、censoring 不再全部混成一个“loss”。

训练若对负例降采样，保存 sampling probability 并在 likelihood 中作逆概率权重；评估和校准始终回到自然总体。

# 8. 优先研究实验：X18-H504-CR-KDJ-PATH

## 8.1 假设

在严格 H504 / Close / Low 联合任务中，与单一 504 日 binary classifier 相比，显式建模“目标达成 vs 先破位”的 competing-risk 时间结构，再加入 KDJ 低位路径持续性和修复后的量压变化，能够减少两类主要误报：

1. 短期冲高但没有收盘站上 4E 的 transient spike；
2. 低位反弹前仍有高破位 hazard 的下跌中继。

这是待验证假设，不是可靠收益声明。

## 8.2 与已做工作的不同

- 不是 H10 High；
- 不是只加几个 KDJ 点值；
- 不是把 `1-label_joint` 全部当一个 loss；
- 不用未来完整性筛候选；
- 利用 event time 和 competing risk，而不是只看504日最终0/1。

## 8.3 同候选实验臂


## 8.4 淘汰标准

任一满足则不继续放大模型：

- 修正候选／账本后增益消失；
- 只靠减少信号量而 precision 上升；
- paired interval 跨 0 且不同 seed 方向不稳；
- 去掉未来确认信息后崩溃；
- 主要 TP 来自一个股票或少数日期簇；
- calibration 严重失真；
- 数据时间预算不足以提供独立 calibration/test。

### 备选 X19：Residualized cross-section

把同日市场热度与个股相对排名分成两个通道：`absolute score` + `within-session residual/rank`，而不是只做 Top-K。验证是否能减少“热市全体分数一起抬高”造成的阈值漂移。

### 备选 X20：Expert quality-gate residual

修规则语义后，使用 base expert raw components 的 residual 信息，strict thresholds 只做 policy，不进入 meta 多列；检验专家机制是否提供 HGB 原始技术指标之外的增量。
