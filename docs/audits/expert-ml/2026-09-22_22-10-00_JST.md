## 0. 本轮结论

新增：

`EML-P1-H504-RECEIPT-PROVENANCE-CALLER-CONTROLLED`

当前 `local_start_receipt.json` 中最关键的三项来源证明：

- `source_sha`
- `effective_prompt_sha256`
- `registered_task_timeout_seconds`

**不是由研究 runner 自己测得，而是 CLI 调用者提供什么就原样写什么。** `run.py` 对前两项默认 `UNKNOWN`，任务上限默认 `None`；`receipts.py` 不核对 Git HEAD、不核对 prompt 文件、不查询 Windows 已注册任务，也不保存训练时工作树 diff/untracked manifest。

因此一个收据即使写着 `evidence_type=REAL_MARKET`，也可以同时声称一个不存在的源码 SHA、一个不是 SHA256 的 prompt hash、一个完全虚构的任务时限，而仍然被正常落盘。**收据当前证明“调用者说了什么”，不是证明“模型实际用什么源码／prompt／父进程上限运行”。**

这与 v5 验收合同直接冲突：开始收据要求 `actual_prompt_hash`、`source/diff hash`、registered timeout；且本地 agent 被允许在同一 session 内继续实现 T1—T5 等缺失分支，所以“启动前 HEAD 是什么”也不足以标识真正进入 fit 的未提交代码。

## 1. 源码证据

### 1.1 `run.py`：三个 provenance 字段都是外部输入

当前 parser：

```python
p.add_argument('--registered-task-timeout-seconds', type=int)
p.add_argument('--source-sha', default='UNKNOWN')
p.add_argument('--effective-prompt-sha256', default='UNKNOWN')
```

`--stage all` 创建收据时直接把这三个 `args.*` 传给 `ResearchSessionReceipt`；没有任何 `git rev-parse HEAD`、prompt 文件哈希或 ScheduledTask 查询／对照。

所以：

- 不传 → `UNKNOWN / UNKNOWN / None`；
- 传错 → 错值照收；
- 传的是启动前值、随后 agent 修改代码 → receipt 仍不变。

### 1.2 `receipts.py`：只序列化，不验证

`ResearchSessionReceipt.write_start_receipt()` 直接写：

```python
'source_sha': self.source_sha,
'effective_prompt_sha256': self.effective_prompt_sha256,
'registered_task_timeout_seconds': self.registered_task_timeout_seconds,
```

没有：

- 实际 Git HEAD；
- tracked diff SHA；
- dirty 路径；
- untracked 研究源码 manifest/hash；
- 实际 prompt 文件 SHA256 的重新计算；
- Windows task 当前 `ExecutionTimeLimit` 的读取与校验。

退出收据虽然会 hash `out_dir` 下结果文件，但不会 hash **实际执行源码树**。所以仅凭 `execution_receipt.json` 无法重建“这次 fit 到底运行的是 HEAD、HEAD+哪个 diff，还是一个临时未跟踪文件”。

### 1.3 launcher 已经知道一部分真值，但没有建立 end-to-end 绑定

`scripts/run_fixup.py` 启动前会测量 `fixup_prompt.txt` SHA256，并写 `launcher_start_receipt.json`；但：

- `registered_task_timeout` 固定写 `NOT_CHECKED_BY_THIS_SCRIPT`；
- 没有把实际 `git rev-parse HEAD` / diff hash 写入 launcher receipt；
- 没有把 launcher 测得的 prompt hash 自动注入 H504 runner；
- DSH agent 启动后仍可在同一工作树修改研究源码，再启动 fit。

也就是说 launcher “启动前干净”只能证明启动瞬间，不证明训练瞬间。

### 1.4 官方本地指令也没有把三项证明完整传进去

`scripts/fixup_prompt.txt` 给出的真实 `--stage all` 命令包含 panel/calendar/candidates/out/resume/offline/evidence-type，但**没有** `--source-sha`、`--effective-prompt-sha256`、`--registered-task-timeout-seconds`。

`RESEARCH_QUICKSTART.md` 的示例补了 `--source-sha <实际源码SHA>`，但仍没有 prompt hash 与 registered timeout；同时它自己承认当前 registry 不是完整的跨进程预算控制器、真实 Windows task 必须本机另查。

因此这不是“只有恶意调用者才能伪造”的边缘情况：**按当前仓库自己的标准执行路径，最完整的 provenance 也不会自动形成。**

## 3. 为什么是 P1，而不是普通日志改进

本项目目前把真实模型结果是否可信建立在多层时间／数据合同上。若 source provenance 不可靠，会出现三个直接问题：

1. **无法复算**：同一个 `source_sha` 收据可能对应不同未提交 diff；看到模型／预测也无法确定产生它的代码。
2. **无法证明三小时链真的满足上限**：`registered_task_timeout_seconds` 现在只是调用者整数，不是机器注册值；填 `13800` 并不等价于 Windows task 真是 `PT3H50M`。
3. **错误复用／归因会被放大**：已有开放项已经确认 signature 对仓库外层 feature producer 存在盲区、registry complete 不核底层 artifact；如果 receipt 的 code provenance 也不可信，三条证据链会同时失去独立交叉校验能力。

本项**不**说明已存在虚假实股成绩；当前仍是 `real_market_fit_count=0`。严重度来自“首个真实 fit 一旦产生，现有 receipt 不能证明它到底由什么源码与 runtime 产生”。

## 5. 建议的最小程序修复顺序

### P1-A：启动 provenance 必须改为 measured，不是 claimed

在真正创建 `ResearchSessionReceipt` 前测量：

```text
actual_head
tracked_diff_sha256
untracked_manifest_sha256
actual_prompt_sha256
actual_registered_task_timeout_seconds
```

真实 `REAL_MARKET/AUX_REAL_HISTORY`：任一关键字段无法测量即 `BLOCKED_RUNTIME_PROVENANCE`，不能继续真实 fit。

### P1-B：每个 fit 绑定 fit-time code snapshot

因为 agent 在一个三小时 session 内允许实现代码，不能只保存 launcher 启动前 HEAD。每个 fit 开始时至少保存：

```text
fit_source_head
fit_tracked_diff_sha256
fit_untracked_manifest_sha256
fit_pipeline_hash
```

registry、model manifest、prediction manifest 都引用同一个 `fit_code_snapshot_id`。

### P1-C：Windows runtime 只接受本机查询值

`registered_task_timeout_seconds` 不再由普通 CLI 参数充当证据。Windows 上从实际 ScheduledTask 读取；非 Windows／查不到任务时写 `UNKNOWN` 并对真实三小时 run fail closed。只有本机回读 `>=13800s` 才允许把 `runtime_config_verified=true` 写进 start receipt。

### P1-D：退出时重新快照

退出 receipt 再测一遍 HEAD/diff/untracked manifest。若 start/fit/end 之间代码发生变化，显式列出变化；不能只靠 out_dir artifact hash。
