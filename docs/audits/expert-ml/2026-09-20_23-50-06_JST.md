## 2. 发现清单

### `EML-P0-AUDIT-FETCH-FAIL-PASS` ── **已确认错误**（本轮从「仍 OPEN」升级）

**文件/函数/行**
- `scripts/scheduled_report_audit.py:84-86`（`changed_reports()` 的失败分支）
- `scripts/scheduled_report_audit.py:108-109`（**唯一**判定行）
- `scripts/scheduled_report_audit.py:141`、`:159`、`:294`、`:354`（`note` 只作展示/日志）
- `scripts/scheduled_report_audit.py:344`、`:376`（同根因：`needs_attention` 与退出码也忽略）

**触发条件/反例**
`git fetch origin main --quiet` 返回非 0。我在**不可达 remote 的临时仓库**里实跑，
得到**真实退出码 128** 与真实 stderr：

```text
fatal: unable to access 'https://invalid.invalid/nope.git/': schannel: failed to receive handshake, SSL/TLS connection failed
```

把这份真实 `(changed=[], note='git fetch failed (exit 128): ...')` 交给脚本**自己的**
`write_status()`（`STATUS` 重定向到临时目录，**不写任何仓库文件**），脚本自己产出：

```text
| Verdict | **PASS** |
| Consistency check | exit code 0 |
| Remote drift | git fetch failed (exit 128): fatal: unable to access ... |
```

**机制**
`note` 只承载「漂移说明」，而判定表达式 `ok = code == 0 and not unstable` 只看
`audit_reports.py` 的退出码 `code` 与「审计期间报告文件被改」`unstable`。
fetch 失败时 `changed = []`（不是 `None`、不抛错），故：
`fetch 失败 → changed=[] → note 变文案 → audit 仍 exit 0 → ok=True → PASS`。

**影响**
把「**无法比较**」发布成「**比较后一致**」。加重项：`:344` `needs_attention` 与
`:376 return 1 if code != 0 else 0` 同样忽略 fetch 失败 →
**进程退出码 0、不写 `FINDINGS.md`、生产启动器 `run_report_audit.cmd:8` 又只传 `--quiet`**，
于是**已提交文件、FINDINGS、stdout、退出码四个通道全都不留失败痕迹**。

**真实发生史（比构造反例更强）**

```text
32155ec (2026-09-19 23:15, 祖先 of HEAD)
   | Verdict | **PASS** |
   | Remote drift | git fetch failed (exit 1): error: fetching ref refs/remotes/origin/main failed: incorrect old value provided |
   All consistency checks passed.

3d1488f (2026-09-18 05:33, 祖先 of HEAD)
   | Verdict | **PASS** |
   | Remote drift | git fetch failed (exit 124): TIMEOUT after 300s: git fetch origin main --quiet |
```

即缺陷**不是理论风险，而是生产运行中已经发布过错误结论**。

**`--dry-run` 是第二入口**：`:82-83 return [], "dry run: skipped fetch"` 与 fetch 失败**同构**，
同样产出 PASS。**但需精确区分**：`--dry-run` 的漂移列文案是 `dry run: skipped fetch`，
**不是**「0 path(s) differ from origin/main」——后者属正常非 dry-run 路径
（生产启动器从不传 `--dry-run`）。

**修复建议**
让 fetch 失败可参与判定：将失败信息作为独立第三个返回值（或让失败返回 `changed=None`），
并令 `ok = code == 0 and not unstable and drift_ok`，同时把 `:344` 与 `:376` 一并纳入 `drift_ok`。
更稳妥语义：fetch 失败时**不发布 PASS**——要么不 commit，要么写
`ATTENTION`/`UNKNOWN` 并显式区分「无法比较」与「比较后一致」。

**验收测试**（建议新增 `tests/test_scheduled_report_audit.py`）
- `test_fetch_failure_is_not_pass`：monkeypatch `run` 使 fetch 返回非 0，断言产出不含 `**PASS**`；
- `test_dry_run_is_not_pass`：断言 `--dry-run` 产出不含 `**PASS**`；
- `test_fetch_success_zero_drift_is_pass`：回归保护，正常绿路径仍为 PASS。

### `EML-P0-COOLDOWN-INDEPENDENT-CLOCK` ── **已确认错误（独立复现上轮反例）**

**文件/函数/行**：`src/labels.py:222-246`，核心在 `:233-234`：
`session_index = {d: i for i, d in enumerate(sorted(out["date"].unique()))}`

**触发条件/反例**（我亲自构造，与上轮声称的 90 会话一致）


**机制**：`session_index` 只由 **signals 里出现过的日期**构建，而**不是市场日历**。
两条信号之间那段「没有任何信号」的市场日被整体跳过，于是在 `positions` 上几乎相邻。

**对照组（证明机制而非偶然）**：连续 200 个市场日都有信号时，保留 4 条，
相邻日历日差 **84/84/84**（60 交易日 ≈ 84 日历日）→ 该情形下冷却**正确**。
即缺陷**只在信号稀疏时触发**，这也解释了为什么它长期未被发现。

**影响**：冷却被静默压缩，`dedupe` 后保留的信号数偏多，
下游 `bull_precision_deduped` 一类指标的分母与「60 会话冷却」的对外口径不一致。
真实触发概率取决于信号稀疏度，**本轮未在真实 signals 上计数**（见 §6 边界）。

**修复建议**：引入独立市场会话轴（一次引入可同时闭合本项与
`EML-P0-ENTRY-ROW-ADJACENCY-ON-REAL-PANEL`），`session_index` 改由日历构建。

**验收测试**：同一股票两次信号真实相隔 ≥ cooldown，断言两条都保留。
