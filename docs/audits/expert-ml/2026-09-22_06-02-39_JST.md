## 4. P1：`prepare_panel` 让“缺 bar”伪装成“有一行但价格缺失”

**ID：`EML-P1-H504-OBSERVED-BAR-PROVENANCE-LOST`**

### 4.1 机制

`data_io.prepare_panel()` 为每只股票按独立 market calendar `reindex(span)`，把停牌/缺 bar 的日期补成一行 OHLCV 全 NaN：

```python
h = g.set_index('date').reindex(span)
h['code'] = code
```

这一步没有保存“原始输入中该 stock-session 是否真的有 bar”的布尔 provenance。

随后 `task_spec.label_h504_candidates()` 再次按 calendar 对齐，并用：

```python
present = cal.isin(g.index)
```

判断该 session 是否有 bar。

问题是：经过 `prepare_panel()` 后，被 reindex 人工补出来的 session 已经进入 `g.index`。因此真正的 missing-bar session 会得到 `present=True`，后续被归类成 `unknown_missing_price`，而不是 `unknown_missing_bar`。

### 4.2 本轮最小复现

本轮在隔离 Python 中按当前两段实现逐步复现：5 个市场日，原始股票数据故意删除第 3 个 session。经过 `prepare_panel` 等价重建后：

```text
missing session OHLC all NaN = True
present mask from index       = True
```

也就是“这一日根本没有原始 bar”与“有 bar 但价格字段坏了”已经无法区分。

### 4.3 影响

用户当前合同明确要求停牌／缺数／退市分开；这项 provenance 丢失会影响：

1. `unknown_missing_bar` vs `unknown_missing_price` 的 outcome 统计；
2. t+1 无 entry 时，究竟是停牌/无 bar 还是坏价格，当前都压成 `no_entry`；
3. 后续删除失／风险建模无法区分数据源缺陷与市场不可交易；
4. 本地 error slicing 会把两种机制混在一起，误导下一轮因子/损失修改。

### 4.4 修复要求

在第一次读原始 panel 时保存不可变字段，例如：

```text
_source_bar_observed = True
```

reindex 新增行自动为 False；`task_spec` 必须读取这个 mask，而不是通过“日期是否在 reindex 后 index”推断。

建议新增回归：

- `test_prepare_panel_preserves_source_bar_mask`
- `test_pipeline_missing_bar_remains_unknown_missing_bar_after_prepare_panel`
- `test_present_bar_with_nan_price_is_unknown_missing_price`
- `test_t1_missing_bar_and_t1_bad_open_are_separately_counted`

## 5. P1：H504 dev 只检查“候选数 >= 50”，没有检查“已解析标签数 >= 50”

**ID：`EML-P1-H504-DEV-RESOLVED-SUPPORT-MISSING`**

### 5.1 机制

`train_h504.run_h504_hgb()` 的 split 资格先按 candidate date 计数：

```python
min_dev_candidates = 50
```

进入实际 dev 后：

```python
dev = data['date'].between(dev_start, dev_end)
resolved = dev & data.label_joint.notna()
```

但阻塞判断只检查：

```python
if train.sum() < min_train_candidates or dev.sum() < 50:
    BLOCKED_PROTOCOL_H504
```

**没有检查 `resolved.sum()`。** 随后 `ydv` 只取 resolved 行，并照常计算 log-loss / Brier；函数最后仍返回 `status='COMPLETE_H504_DEV'`。

### 5.2 本轮算术复现

sklearn 对单个已解析负例完全可以返回有限指标：

```text
y = [0], p = [0.2]
log_loss(labels=[0,1]) = 0.2231435513
Brier                  = 0.04
AP                     = None
```

因此“dev 有 50 个候选，但只有 1 个 resolved”并不会因 metric API 报错而自然失败；当前代码可能把它标成 `COMPLETE_H504_DEV`。

### 5.3 影响

H504 的 missing/no-entry/unknown 很可能不是均匀随机。若选择 dev block 时只看候选数、不看 resolved support：

- 可以对极少 resolved 样本产生看似正常的 log-loss/Brier；
- 不同模型/因子可能在不同 unknown 结构下比较，误把数据可观测性当模型增量；
- `COMPLETE_H504_DEV` 的语义过强，容易被上层页面当作一个有效开发折。

### 5.4 修复要求

不要简单在选中第一折后发现 resolved 少就直接终止；应该遍历结构合法的 splits，选第一个同时满足：

- actual mature train >= `min_train_candidates`
- actual resolved dev >= `min_dev_resolved`（建议起点 50）
- dev unknown/no-entry 数量仍完整保留并单列

零正例 dev 可以保留为有效“负面块”，但不能把 AP 写成 0；模型选择时应同时报告事件支持和 `n_dev_resolved`。

建议新增：

- `test_h504_does_not_complete_dev_with_50_candidates_but_1_resolved`
- `test_h504_skips_early_unknown_heavy_dev_and_uses_later_supported_block`

## 6. P1：48-fit 累计预算目前只是 prompt 合同，没有代码级强制

**ID：`EML-P1-H504-GLOBAL-FIT-BUDGET-UNENFORCED`**

当前 `Registry` 只提供 `latest_complete(signature)`；`run.py` 的 `nfit` 只限制**本次 AUX 循环** `--max-aux-fits`，没有读取历史 registry 后计算：

```text
cumulative_started / failed / interrupted / completed / remaining_of_48
```

集成验证 JSON 自己也明确写了：

> Registry does not replace a global fit-budget controller; local executor must enforce remaining 48-fit cap.

这不是文档错误，而是当前三小时合同尚未程序化。随着下一步补 T1—T5、MLP、消融、error-driven refit，同一 session 或跨 session 很容易超出 48-fit 旧预算，尤其失败/中断/重试按合同也必须计数。

### 修复要求

给 registry 增加不可重置的预算视图，至少记录：

- `fit_attempt_id`
- `signature`
- `task_scope`
- `started_at / ended_at`
- `status`
- `counts_against_budget`
- `parent_session_id`

runner 启动任何新 fit 前原子检查剩余预算；`REUSED_COMPLETE` 不重复计数，但 `FAILED / INTERRUPTED` 要计数。预算耗尽必须以 `BUDGET_EXHAUSTED` 结束并留下剩余 READY 队列。

## 7. P2：AUX 在 epoch 中间被杀后，恢复路径会给部分样本额外训练权重

**ID：`EML-P2-AUX-PARTIAL-EPOCH-RESUME-WEIGHTING`**

`aux_tcn.py` 在 batch 循环中发现 deadline 后：

```python
_checkpoint(last_path, epoch)
```

此时 checkpoint 保存的是**已经做完若干 batch optimizer.step() 的部分 epoch 模型**。下一次加载后：

```python
start_epoch = ck['epoch']
```

会从这个 epoch 重新创建/迭代完整 DataLoader。于是中断前已经吃过的样本会在“部分 epoch + 重跑完整 epoch”中获得额外一次更新机会；它不是仅仅“非 bit-exact”，而是可能改变样本权重路径。

仓库验证文件已经诚实声明“不保证 epoch 内 bit-exact”；本轮进一步把这个限制具体化为 paired base-vs-plus 可比性风险。

### 建议

在没有 batch-cursor/sampler 精确恢复前，研究口径更稳妥的是 **epoch-boundary rollback**：

- 每个 epoch 开始前保留上一完整 epoch checkpoint；
- 中途 deadline 只标 interruption，不保留部分 epoch optimizer/model 作为继续起点；
- 下一次从最后一个完整 epoch 重跑。

损失少量计算时间，换取确定的样本暴露次数；对于需要做 paired attribution 的研究更合适。
