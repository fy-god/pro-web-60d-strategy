## 0. 本轮结论

前一份报告把 peer 的 §3.3「别名冲突」记为**未复现**并更正为「键空间分裂」。本轮把该更正**做成可执行反例**，并实测出比 peer 原文更严重的后果：

**一个逻辑证券（同一日期、同一真实标的）在同一个面板里用两种合法编码表示时，标签阶段会产生两条账本行、两个不同的 `entry_open`，并且不抛任何异常。**

peer 的原文预言的是「碰撞/合并」，实际发生的是**分裂**——而分裂比碰撞更隐蔽：碰撞会报错，分裂不会。

## 1. 可执行反例（我亲自跑，非转述）

构造：`code=1` 且 t+1 `open=51.0`；`code="000001"` 且 t+1 `open=11.0`；同一交易日。

```text
raw panel duplicated(['code','date'])      = False
prepare_panel(...)                         -> rows=12, codes=['000001','1'], RAISED=no
after prepare_panel duplicated(...)        = False        <-- 重复守卫被绕过
distinct code keys surviving               = 2            (只有 1 个逻辑证券)

标签阶段产物（candidates 走外部文件路径）:
  code='000001'  entry_open=11.0  outcome_class='timeout'
  code='1'       entry_open=51.0  outcome_class='timeout'
  rows = 2   distinct entry_open = [11.0, 51.0]   ANY error raised? NO
```

对照（同一份数据走 candidate manifest）：

```text
build_candidate_manifest(...) -> ValueError: duplicate candidate key(s)
```

### 机制

- `data_io.py:25` 只做 `astype(str)`，因此 `1` 与 `"000001"` 是**两个不同的字符串键**；
- `data_io.py:26` 的 `duplicated(['code','date'])` 因此**不触发** —— 守卫在语义上是对的，但作用在未规范化的键空间上，故对别名无效；
- `task_spec.py:70-71` 用该键建 `arrays[code]`，`:95` 用同键查找；两个键都查得到，于是**各自产生一条独立账本行**；
- `candidate_manifest.py:39` 会补零，使两个别名收敛到同一键，并在 `:58` **fail closed**（`)` raise）。因此**只有外部 `--candidates` 路径**（`run.py:117`，跳过 manifest 构建）才暴露此分裂。

### 影响

被污染的是一份**看起来完全正常**的 outcome 账本：同一真实证券贡献两行、两个入场价，直接改变 resolved 计数、自然分母与后续 fold/fit 的样本构成，且没有任何异常、没有告警字段。

**如实限定**：该路径需要「外部提供混合编码的候选/面板」。仓库自身管线始终补零（实测 5 个真实产物 `code` 全为 6 位、非 6 位计数 0），仓库内也**不存在**任何 H504 账本产物（`real_market_fit_count=0`）。因此**错误值从未出厂**，本项记为**待验证风险 / 首跑前置门**，不是已确认错误。
