1. 找到最新的专家/ML 审计报告
2. 读懂它指出的问题
3. 修改代码
4. 验证
5. 提交并推送

**绝对不要**自己写审计报告、不要新建报告文件、不要往 `docs/audits/expert-ml/` 里写任何东西。那个目录由 GPT Pro 网页版负责产出。你只读它，不改它。

## 仓库

`D:\ccc\pro-web-60d-strategy`（当前工作目录就是它）

## 第 1 步：找到要处理的报告

报告在 `docs/audits/expert-ml/`，文件名格式 `YYYY-MM-DD_HH-mm-ss_JST.md`。

先读 `logs/fixup/last_processed.txt`（如果存在），里面是上一轮已处理的报告文件名。然后：

- 列出 `docs/audits/expert-ml/` 里所有 `YYYY-MM-DD_HH-mm-ss_JST.md` 格式的文件，按名字降序 = 时间降序，最新在前
- 忽略 `LATEST.md` 和 `SCHEDULE.md`（它们不是报告）
- 取最新的那一份

**如果最新报告 == `last_processed.txt` 里的名字**：说明本轮没有新报告，GPT Pro 还没发布。这时候**什么都不要做**，直接结束并输出 `NO_NEW_REPORT`。不要重做上一轮，不要编造工作。

**如果 `logs/fixup/last_processed.txt` 不存在**：先看 `git log --oneline -15` 判断哪些报告已经被处理过（提交信息里会提到）。保守起见，只处理最新的那一份，不要回溯处理全部历史报告。

## 第 2 步：读懂报告

报告是中文的，会按 P0 / P1 / P2 列出问题，每条包含：文件、函数、真实行号或最小代码、触发条件、机制、影响、改法、验收测试。

**只处理 P0 和你有把握的 P1。** 不要试图一次做完所有 P2。

## 第 3 步：改代码前必须复现

这是最重要的一步。**先写一个独立脚本复现报告说的问题，确认它真的存在，再改。**

报告可能是错的。之前的真实教训：
- 有报告说某个测试变量是死代码，删掉后审计直接崩溃（`NameError`）
- 有报告说某个测试能抓住某个缺陷，实测根本抓不住

**如果复现不出来，就在报告里记下"无法复现"，跳过这一条，不要瞎改。** 宁可少改，不可改错。

复现脚本放 `scripts/scratch/_repro_*.py`，用真实数据或最小合成数据。

## 第 4 步：改代码

- 改完必须解释**为什么这样改**，用注释记录机制，不要写"修复 bug"这种废话
- 如果改动影响已发布的数字，**必须量化影响范围**（多少行受影响、是否改变结论），再决定要不要重新生成产物
- 新增或修改行为要有**回归测试**，并且验证这个测试真的能抓住缺陷（把缺陷改回去，测试必须失败）

## 第 5 步：验证

必须全绿才能提交：

```
set PYTHONPATH=.
python -m pytest tests/ -q
python scripts/audit_reports.py
```

`audit_reports.py` 必须 `0 problem(s)`。如果有 FAIL，先搞清楚是你改坏的还是本来就有。

环境注意：
- Python 默认编码是 GBK。读 JSON 用 `io.open(path, encoding='utf-8')`，不要用 `json.loads` 直接读文件
- `print()` 遇到 `†`、`×` 这类字符会抛 `UnicodeEncodeError`
- 不要留一堆 python 进程，跑完就结束
- 临时脚本用完删掉

## 第 6 步：提交推送

```
git add <具体文件>          # 不要用 git add -A，会扫进垃圾文件
git commit -F <消息文件>    # 提交消息写清楚：哪个报告、哪几个 P0、怎么复现的、影响范围
git fetch origin main
git rebase --autostash origin/main
git push origin HEAD:main
```

**提交消息要用中文或英文写实质内容**，说明：
- 哪个报告（文件名）
- 修了哪几条，每条的 P0/P1 编号
- 怎么复现的
- 影响范围（是否改变已发布数字）
- 验证结果

**推送前先 `git fetch` 再 rebase**，因为这个仓库有另一个自动化也在推 `main`。裸 `git push` 会输给竞态。

如果推送失败，重试最多 3 次（每次先 fetch + rebase）。

## 第 7 步：记录

成功了才写 `logs/fixup/last_processed.txt`，内容是这次处理的报告文件名。

## 结束输出

用简短中文总结：
- 处理的报告文件名
- 修了什么（P0/P1 编号 + 一行说明）
- 哪些无法复现、跳过了
- 验证结果（测试数、审计检查数）
- 推送的 commit hash

如果这轮没新报告，只输出 `NO_NEW_REPORT`。
